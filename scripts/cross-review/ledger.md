# 지적 원장 형식

PR마다 리뷰 지적의 등급과 처리 상태를 추적하는 PR 댓글이다(설계서 10.2절 (4)·(5)). 기록 job이 검증 App으로 쓰고, 작성 에이전트는 고치지 않는다. 구현은 `scripts/ci/ledger.ts`다.

## 댓글 구성

```markdown
<!-- harness-ledger:v1 -->

## 지적 원장

기록 job이 관리한다. … 프롬프트 버전: `<1라운드 base SHA 앞 12자>` · 라운드: claude 2, codex 1

| ID  | 등급 | 검증자 | 위치           | 내용               | 재현   | 상태  | 처리    |
| --- | ---- | ------ | -------------- | ------------------ | ------ | ----- | ------- |
| F1  | P1   | codex  | src/auth.ts:42 | 만료 토큰을 허용함 | 재현됨 | fixed | a1b2c3d |

<!-- harness-ledger-data:<base64 JSON> -->
```

- 표는 사람이 읽는 것이다. 기계는 마지막 줄의 숨은 자료만 읽고, 표는 그 자료에서 다시 만든다.
- 숨은 자료가 없거나 둘 이상이거나 형식이 다르면 원장으로 읽지 않는다.
- 표 셀의 글은 한 줄로 만들고, 마크다운·HTML·멘션으로 해석될 문자를 문자 참조로 바꾼다.
- 지적의 근거와 제안 본문은 원장에 넣지 않는다. 기록 job 로그에 남는다.

## 숨은 자료

| 필드         | 내용                                                                               |
| ------------ | ---------------------------------------------------------------------------------- |
| `version`    | 1                                                                                  |
| `promptBase` | 1라운드의 base SHA. 이 PR의 모든 라운드가 이 버전의 프롬프트를 쓴다                |
| `rounds`     | 판정마다 `{ reviewer, head }`. 검증자별 라운드 수와 직전 판정 head를 여기서 얻는다 |
| `findings`   | 지적 목록(아래)                                                                    |
| `ciFailures` | `check` 실패 기록 `{ head, run }`                                                  |
| `dropped`    | 원장이 가득 차(150건) 등록하지 않은 P2·P3 수. P0·P1은 가득 차도 등록한다           |
| `planReview` | 계획 승인 `{ hash, head, approvals }`(아래 "계획 승인"). 없을 수 있다              |

지적 하나: `id`(`F<번호>`), `severity`, `reviewer`(`claude` \| `codex`), `file`, `line`, `title`, `repro`(`''` \| `reproduced` \| `not-reproduced` \| `error`), `status`, `note`(처리), `round`(그 검증자의 몇 번째 판정에서 등록됐는가), `rejectedBy`(P0을 `rejected`로 보자고 한 검증자).

## 상태

| 상태       | 뜻                                                                       |
| ---------- | ------------------------------------------------------------------------ |
| `open`     | 해소되지 않은 P0·P1. 병합을 막는다                                       |
| `fixed`    | 지적을 낸 검증자가 수정을 확인했다                                       |
| `rejected` | P1은 지적을 낸 검증자가 반박에 동의했다. P0은 두 검증자가 모두 동의했다  |
| `deferred` | P2·P3이거나 동결된 지적이다. 후속 PR이나 `tech-debt-tracker.md`로 넘긴다 |

## 계획 승인 (G1)

중·대 규모 계획의 교차 검증 승인이다(설계서 4.1절, 10.3절 승인 결속 기준). `plan-gate`가 읽는다.

- `hash`: 승인받은 계획 핵심 섹션 해시(sha256 64자, `scripts/ci/plan-hash.ts`). `head`: 승인이 마지막으로 기록된 PR head. `approvals`: 그 해시를 승인한 검증자.
- PR이 계획 폴더만 바꾼 head(`mode=plan`)의 판정으로만 기록한다. 코드가 섞인 head의 판정은 이 필드를 바꾸지 않는다.
- 그 head에서 `review/<검증자>`가 success면(승인, 위험도 기준 "해당 없음", 이어받음) `approvals`에 넣는다. failure면 그 검증자를 빼고, error면 그대로 둔다.
- 판정한 head의 해시가 기록된 해시와 다르면 이전 승인을 모두 지우고 새 해시로 다시 시작한다.
- 계획 승인이 있으면 지적이 없어도 원장 댓글을 만든다. 댓글에는 `계획 검증(G1): 해시 … · 승인: … · head …` 한 줄로 보인다.
- 이 필드는 `review-ledger` 판정에 영향을 주지 않는다. 이 필드가 생기기 전에 만들어진 원장에는 없다.

## 판정 반영 규칙

- 새 지적은 P0·P1이면 `open`, P2·P3이면 `deferred`로 등록한다. 같은 검증자·위치·제목의 지적은 다시 등록하지 않는다. 그 지적이 `fixed`·`rejected`였으면 회귀로 보고 `open`으로 되돌린다.
- 근거(`evidence`)나 위치(`file`)가 빈 P1은 P2로 내려 등록한다(처리 칸에 이유). P0은 내리지 않는다.
- 동결: 그 검증자의 2라운드부터, 직전 판정 head 이후 바뀌지 않은 파일의 새 P1은 `deferred`로 등록한다. P0과 재현 job이 재현한 P1은 `open`으로 받는다.
- 재현 칸은 재현 job의 결과다(`reproduced` 재현됨, `not-reproduced` 재현 안 됨, `error` 실행 못 함). PR 코드가 실행된 결과라 조작될 수 있다. "재현 안 됨"·"실행 못 함"은 상태를 바꾸지 않는다.
- 검증자는 판정의 `resolutions`(`{ id, status, note }`)로 원장 지적의 상태를 낸다. 자기 지적의 `fixed`·`rejected`·`open`만 반영한다. 남의 지적에 대한 판정은 P0의 `rejected` 동의만 기록한다.
- `deferred` 지적은 판정으로 바뀌지 않는다.
- `review-ledger`는 `open`인 P0·P1이 없을 때만 통과한다. 동결돼 `deferred`로 등록된 P1은 막지 않고(설계서 10.2절 (5)), 그 수를 상태 설명에 적는다.
- 댓글 본문이 60000자를 넘게 되는 P2·P3은 등록하지 않고 센다(`dropped`). P0·P1은 크기와 상관없이 등록한다.
- 라운드 기록은 자르지 않는다. 라운드 번호와 동결 판정의 근거다.
