# 하네스 엔지니어링 설계 평가

> 검토 대상: `하네스엔지니어링.md` v0.5 (2026-11-10)
> 비교 기준: `openai.md` — OpenAI의 하네스 엔지니어링 글
> 평가일: 2026-11-10
> 범위: 설계 검토. 구현 및 테스트는 수행하지 않았다.

## 총평

OpenAI 글의 중심 아이디어인 **에이전트가 읽기 쉬운 저장소, 짧은 진입 문서와 구조화된 지식, 기계적으로 강제하는 아키텍처 규칙, 에이전트가 직접 검증하는 피드백 루프**를 잘 반영했다. 작업 기록과 앱 관측성을 나눈 점, 규칙의 보장 수준을 구별한 점, 위험 작업을 권한으로 제한하려는 점도 설계의 강점이다.

원문이 경험을 통해 발전시킨 하네스 사례라면, 이 문서는 이를 1~2인 운영·두 AI 도구·GitHub 기반 자동 병합에 맞춘 구체적인 운영 설계로 확장했다. 그 선택을 원문과 다르게 가는 이유까지 기록한 것도 좋다.

현재 준비도는 **설계 문서로는 높고, 무인 자동 병합을 시작하기에는 아직 이르다.** 가장 큰 이유는 `pull_request_target`에서 PR을 읽는 LLM 검증 job과 인증정보의 경계, 그리고 로컬 에이전트의 실행 권한이다. 하네스 보호 경로를 구축 중 자동 병합하는 방침은 사용자의 명시적인 단계별 선택으로 이해하며, 그 자체를 치명 결함으로 분류하지 않는다. 다만 구축 단계가 언제 끝나는지와 운영 제어가 언제 켜지는지는 기계적으로 확인할 수 있게 해야 한다.

## 치명적인 것

### 1. `pull_request_target`의 main 전용 environment가 PR을 격리하지 않는다

**위치:** 10.4절(717~728행), 13.3절(879~883행), Q20

LLM 판정 job은 `pull_request_target`에서 실행되고 Claude·Codex 인증정보는 main 전용 environment에 둔다. 하지만 GitHub은 `pull_request_target`의 `GITHUB_REF`를 PR의 head가 아니라 **base 브랜치**로 설정한다. 따라서 main을 대상으로 한 PR의 이벤트 ref도 main이어서, environment를 main 브랜치에만 허용하는 설정만으로는 해당 PR을 배제하지 못한다. GitHub은 이 이벤트를 비밀과 권한이 있는 고신뢰 컨텍스트로 설명하고, 신뢰할 수 없는 PR 코드를 실행하지 말라고 경고한다. [이벤트 ref 설명](https://docs.github.com/en/actions/reference/workflows-and-actions/variables), [`pull_request_target` 보안 지침](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target)

PR 코드를 실행하지 않더라도, PR diff와 문서는 LLM 입력이다. 이 입력을 처리하는 프로세스에 구독 인증정보가 함께 있으면, 정확히 같은 토큰 문자열을 찾는 출력 필터만으로는 유출을 충분히 막을 수 없다.

**수정 권고:** main 전용 environment를 PR 격리 장치로 간주하지 않는다. 인증정보를 쓰는 job과 PR 입력을 처리하는 job의 권한·프로세스 경계를 다시 설계하고, LLM 판정 job에는 셸·MCP·불필요한 네트워크·GitHub 쓰기 권한을 주지 않는다. 실제 비밀 대신 가짜 토큰을 둔 테스트 PR로 `pull_request_target`에서 어떤 ref와 environment 권한이 적용되는지 먼저 검증한다.

### 2. 무인 작업에 필요한 L0 격리가 로드맵 후반에 있다

**위치:** E5(38행), 13.2절(865~874행), 기존 프로젝트 도입 순서(1031~1040행), 로드맵(1114~1120행)

에이전트는 제작자와 같은 Mac 사용자로 실행하고 E5는 “권장”이다. 반면 L0 샌드박스는 기존 프로젝트 도입의 마지막 단계이며, 로드맵에서도 4단계에 도입한다. 이 기간에는 제작자 토큰을 실수로 사용하지 않도록 훅에 의존하더라도, 훅이 없는 도구·우회된 명령·다른 개발 도구의 인증정보에 대한 접근은 막힌다고 볼 수 없다. Codex 훅과 각 플랫폼의 샌드박스 지원도 아직 열린 질문(Q4)이다.

이는 R20의 제작자 권한 차단을 “사실상 차단”으로 보는 근거를 약하게 하고, B9의 권한 중심 원칙과도 맞지 않는다. 실제 제품 리포나 무인 세션에 적용하기 전에는 격리 경계를 필수 전제조건으로 삼는 편이 안전하다.

**수정 권고:** 에이전트 작업공간에는 봇 계정과 제한된 개발·테스트 자격증명만 두고, 제작자 계정·키체인·SSH·클라우드 인증정보와 분리한다. 별도 OS 사용자, 일회용 VM/컨테이너, 호스팅 작업공간 중 구현 가능한 방식을 선택해 L0가 실제로 worktree 밖 파일과 네트워크 접근을 차단하는지 확인한다. 훅은 편의·빠른 피드백 장치로 유지한다.

## 보통

### 1. 구축 단계의 자동 병합은 의도된 예외로 두되, 종료 조건을 명확히 한다

**위치:** 10.4절(730~749행), 16절(1031~1040행), 19절(1108~1121행)

사용자는 하네스를 만드는 동안 보안 제어 파일마다 승인을 요구하면 개발이 번거로우므로, 완성 시점에 제어를 켜겠다고 설명했다. 이를 반영하면 구축 단계의 보호 경로 자동 병합은 설계 의도를 가진 **임시 위험 수용**이며, 현재의 치명 결함으로 보지 않는다.

다만 로드맵은 1단계에서 자동 병합을 켜고, 교차 검증·`harness-guard`·하네스 자체 테스트의 상당 부분은 2단계 이후에 둔다. 따라서 1단계는 완성된 하네스의 운영 기준이 아니라, 안전장치가 아직 덜 갖춰진 부트스트랩 구간이다.

**수정 권고:** “완성”을 배포 가능한 체크리스트로 정의한다. 예를 들어 필수 상태 체크와 검증 App 출처 확인, 보호 경로 승인 설정, 봇의 `workflows` 쓰기 권한 회수, 하네스 자체 테스트 및 빈 테스트 리포의 전체 흐름 통과를 완료 조건에 넣는다. 실제 제품 프로젝트에 복사하거나 파일럿을 시작하기 전에 이 조건을 충족하도록 명시한다. 개발 중 매 PR을 수동 승인하라는 뜻은 아니다.

### 2. Codex CI 인증의 운영 가능성을 2단계 착수 전에 확인한다

**위치:** 13.3절(876~885행), Q12·Q20

`auth.json`을 러너에서 복원하고 갱신본을 저장하는 흐름은 문서에서도 구현 시 확인하도록 남겨 두었다. 이는 단순 구현 세부가 아니라 CI의 인증 방식, 장기 자격증명 보관, 사용량·계정 잠금 리스크를 결정한다. 현재 OpenAI 공식 문서에는 Codex를 위한 workload identity federation 경로가 있지만 관리형 ChatGPT 워크스페이스 대상의 베타 기능으로 안내되어 있어, 개인 구독 중심 설계에 바로 맞는다고 가정할 수 없다. [Codex workload identity 안내](https://developers.openai.com/api/docs/guides/workload-identity-federation)

**수정 권고:** Q20의 시험을 2단계 착수 전 차단 조건으로 올린다. 실제 구독·개인 계정에서 CI 비대화 실행, 인증 갱신, 동시 실행 제한, 토큰 재저장, 사용량 한도 도달 동작을 작은 테스트 리포에서 확인한다. 지원되지 않거나 유지 비용이 크면 CI 전용 인증 방식과 예산 통제로 재설계한다.

### 3. `patch-id`가 같아도 재검토를 생략할 범위를 제한한다

**위치:** 10.3절 승인 결속 기준(676~686행)

rebase 뒤 patch-id가 같다는 것은 변경 패치가 유사하다는 신호이지, 새 base와 결합된 코드의 의미까지 같다는 증거는 아니다. `check`를 재실행하는 것은 유용하지만, 코드의 의미가 base 변경으로 달라진 경우 리뷰 판정까지 자동 승계하는 것은 약하다.

**수정 권고:** 기준 브랜치가 바뀐 뒤에는 최종 병합 대상 기준으로 테스트를 다시 돌린다. 보안·권한·인증 변경과 위험도 “높음” PR은 patch-id가 같더라도 LLM 재검증을 요구한다. 개인 저장소에서 merge queue를 쓸 수 없는 경우에도 동등한 최종 병합 검증 경로를 정한다.

### 4. 계획 상태 `completed`와 실제 병합의 순서를 맞춘다

**위치:** 8.3절(계획 상태 전이·완료 처리), 10.3절(667행, 688~693행)

`plan-gate`는 병합 전에 계획 상태가 `completed`인지 확인하지만, 완료 처리는 검증 승인 후 계획 전용 커밋으로 한다고 적혀 있다. “승인”이 LLM 리뷰 승인인지 실제 GitHub 병합인지에 따라 실행 순서와 계획 상태의 의미가 달라진다. 새 커밋이 생기면 위험도 높은 변경의 제작자 승인은 head SHA에 묶여 다시 받아야 하는 점도 함께 고려해야 한다.

**수정 권고:** 병합 전 상태(예: `ready_to_merge`)와 실제 병합 뒤 상태(`completed`)를 분리하거나, 계획 완료 커밋을 병합 전 넣는 이유와 실패 시 되돌리는 규칙을 명시한다. `plan-gate`와 승인 결속 기준이 이 전이와 일치하는지 확인한다.

### 5. 범용 코어와 초기 구현 범위가 크다

문서는 GitHub·Claude Code·Codex를 전제로 하면서 웹·게임 프로파일, 다양한 DB와 운영 환경까지 포괄한다. 동시에 문서에는 아직 결정 전인 구현 선택(Q1, Q3, Q10 등)도 남아 있다. 모든 구성요소를 구현하기 전에 범용성을 먼저 완성하려 하면 유지 비용이 커질 수 있다.

**수정 권고:** 첫 실사용 프로파일을 웹 하나로 고정하고, 공통으로 반복 확인된 계약만 코어에 올린다. 게임 프로파일, Tier 2 관측성, 중앙 배포 방식 같은 확장은 실제 필요가 생길 때 추가한다. 현재 로드맵의 “최소 구성 후 실패에 따라 확장” 원칙과도 잘 맞는다.

## 선택

- **Tier 2 관측성:** 로그·메트릭·트레이스의 별도 스택은 성능 예산이나 재현 문제로 필요성이 확인될 때 도입해도 된다. 첫 파일럿은 구조화 로그와 웹 검증으로 시작할 수 있다.
- **주간 정기 작업:** doc-gardening·품질 점수·드리프트 정리의 주기는 실제 문서 드리프트와 작업량을 관찰한 뒤 조정한다.
- **400줄 PR 경고:** 이미 경고부터 시작하도록 설계되어 있다. 파일럿에서 리뷰 라운드, 리드타임, PR 목적 분할이 실제로 좋아지는지 보고 기본값을 정하면 된다.

## 권장 수정 순서

1. `pull_request_target`에서 base ref와 environment 권한을 확인하고, LLM 인증정보 경계를 다시 설계한다.
2. 실제 제품 파일럿 전에 제작자 자격증명과 에이전트 작업환경의 격리 수준을 확정한다.
3. 구축 단계 자동 병합은 임시 예외로 유지하되, 하네스 완성·운영 전환 체크리스트를 만든다.
4. Q20 인증 실험, patch-id 적용 범위, 계획 상태 전이를 파일럿 전 완료 조건으로 둔다.

## 결론

v0.5는 이전 버전보다 보안 경계와 운영 제어를 구체적으로 설명하며, OpenAI 글의 원칙을 사용자의 자동화 목표에 맞춰 확장했다. **구축 중 보호 경로 자동 병합은 사용자의 의도에 따른 임시 선택으로 인정한다.** 다만 `pull_request_target`의 인증 경계와 로컬 에이전트 권한은 그 편의 선택과 별개의 문제이므로, 실제 제품에 적용하기 전에 검증이 필요하다. 그 두 항목과 운영 전환 조건을 보완하면 웹 파일럿으로 진행할 수 있는 설계가 된다.
