## 총평

원문의 뼈대는 충실히 옮겼습니다. `AGENTS.md`를 지도로 쓰고 `docs/`를 기록 시스템으로 두는 구조, 실행 계획, 수정 지침을 담은 린트 에러 메시지, 엔트로피 정리, worktree별 앱 실행이 모두 들어 있습니다. 원문과 다르게 간 부분(차단 게이트를 늘리고 사람 없이 자동 병합)은 3.1절에 이유와 함께 적었습니다. 1~2인 팀이 무인으로 병합하는 조건에서는 타당한 방향입니다. 보장 수준 구분(차단·검출·절차), "절차" 규칙마다 최대 피해를 적는 방식, 10.2절 리뷰 수렴 규칙, 원칙 B11(LLM은 차단을 더할 수만 있다)은 그대로 써도 됩니다.

남은 문제는 대부분 **GitHub Actions가 실제로 어떻게 동작하느냐**에서 나옵니다. 문서의 논리는 맞지만, 플랫폼 동작 때문에 보장이 깨지거나 루프가 멈추는 곳들입니다. 문서를 더 다듬기보다 Q20 빈 리포 실험을 지금 시작하는 편이 낫습니다.

**분류 기준**
- **치명**: 이대로 만들면 문서가 "차단"이라 적은 보장이 깨지거나 자동 병합 루프가 돌지 않습니다. 구현 전에 고쳐야 합니다.
- **보통**: 안전은 유지되지만 오작동, 비용 낭비, 잘못된 판정으로 이어집니다. 파일럿 전에 고칠 것입니다.
- **선택**: 고치면 좋은 것입니다.

## 치명

### 1. 필수 체크의 출처 지정이 `review/*`에만 걸려 있습니다 (46행)

- `risk-gate`, `plan-gate`, `review-ledger`, `harness-guard`, `deps-guard`, `revert-check`도 기록 job이 쓰는 상태인데, 출처는 `review/*`만 지정했습니다. 출처를 지정하지 않은 필수 체크는 **이름만 맞으면 누가 쓴 상태든 인정됩니다**.
- 구축 단계의 봇(`workflows` 쓰기 권한, 34행)과 외주 개발자(개인 리포 협업자는 쓰기 권한을 가짐)는 아무 브랜치에나 `push` 워크플로를 올릴 수 있습니다. 그 워크플로 YAML에서 `permissions: statuses: write`로 권한을 올릴 수 있습니다. 리포의 "읽기 전용"은 기본값일 뿐 상한이 아닙니다.
- 그 토큰으로 **다른 PR의 head SHA에** `risk-gate = success`를 쓸 수 있습니다.
- 이 브랜치는 PR이 되지 않으므로 `harness-guard`도 검증자도 보지 못합니다. 그러면 마이그레이션이나 인증 PR이 제작자 승인 없이 병합되고, R13의 "차단"이 사라집니다.
- `check`도 같은 방식으로 위조할 수 있습니다. 둘 다 GitHub Actions 출처라 구분이 안 됩니다.

**제안**
- `check`를 뺀 모든 필수 체크의 출처를 검증 App으로 지정합니다.
- `check`는 기록 job이 해당 SHA의 `pull_request` 실행을 워크플로 경로까지 확인한 뒤, App 상태(`ci/check`)로 다시 기록합니다. 필수 체크로는 이 `ci/check`를 등록합니다.
- main 정의 워크플로의 `workflow_dispatch` 입력도 공격자 입력으로 다룹니다. 브랜치 워크플로가 `actions: write`로 main 워크플로를 호출할 수 있기 때문입니다.

### 2. 재현 job이 `pull_request_target`에서 PR 코드를 실행합니다 (716행)

- `pull_request_target` 실행은 **main의 캐시 범위**에서 돕니다. 표에 적힌 "캐시 공유 없음"은 job 설정으로 끌 수 있는 것이 아닙니다.
- GitHub 호스팅 러너에는 sudo가 있습니다. PR 코드가 러너 프로세스에서 캐시 쓰기 토큰을 꺼내 main 캐시를 오염시키는 기법이 2024년에 공개되었습니다.
- 그 캐시를 복원하는 job이 장악됩니다. App 키를 가진 기록 job, 구독 토큰을 가진 판정 job, 봇 토큰을 가진 revert 워크플로가 대상입니다. App 키 유출은 자격증명 표(914행)가 스스로 "치명"이라 적은 항목입니다.
- 재현 job을 main 정의로 돌려서 얻는 이득도 거의 없습니다. PR 코드를 실행하는 한 결과는 조작될 수 있다고 이미 인정했습니다(723행).

**제안**: PR 코드를 실행하는 작업은 모두 PR이나 브랜치 범위에서 돌립니다.
- `check`는 지금처럼 `pull_request`로 둡니다.
- 재현 job은 PR head 브랜치를 ref로 하는 `workflow_dispatch`로 옮깁니다. 비밀이 없고, 캐시는 그 브랜치 범위에 남습니다.
- 판정, 기록, 그 밖의 게이트는 `pull_request_target` 대신 **`workflow_run`**(check 완료 후 실행)으로 옮깁니다.
  - 지금은 판정 job이 check와 동시에 시작되어, 기다리려면 폴링이 필요합니다. `workflow_run`으로 바꾸면 R16의 "check를 통과한 커밋에서만 검증"도 함께 강제됩니다.
- 비밀을 가진 job은 캐시를 복원하지 않습니다. `setup-*` 액션의 cache 옵션도 끕니다. 아티팩트는 스키마 검사를 통과한 뒤에만 씁니다.

### 3. Codex 검증자는 "셸 없이" 실행할 수 없습니다 (532행, 997행)

- 제가 아는 한 Codex CLI는 셸 명령(`sed`, `rg`, `cat`)으로 파일을 읽습니다. read-only 샌드박스는 쓰기와 네트워크만 막고, 읽기 범위는 막지 않습니다. 따라서 Codex 검증자는 자기 `~/.codex/auth.json`을 읽을 수 있습니다.
- 유출 경로는 이렇습니다.
  1. PR diff에 지시문을 심습니다.
  2. 검증자가 auth.json을 읽고, 지적 본문에 변형해서 담습니다(공백 삽입, base64, 일부만 등).
  3. 기록 job의 **정확 일치** 검사(722행)를 통과합니다.
  4. PR 댓글로 공개됩니다.
- 유출되는 것은 제작자 ChatGPT 계정의 refresh token입니다. 이 댓글은 외주 개발자와 작성 에이전트가 읽습니다. L0가 4단계에야 들어오므로, 1~3단계에서는 작성 에이전트가 토큰을 외부로 보낼 수도 있습니다.

**제안**
- 10.4절 표를 사실대로 고칩니다. Codex는 "셸 있음, 쓰기·네트워크 없음, 러너 전체 읽기 가능"입니다.
- 기록 job의 검사를 바꿉니다. 고엔트로피 문자열, 긴 영숫자 연속, 비밀 값의 부분 문자열(예: 8자 이상)을 차단하고, 지적 본문 길이 상한을 짧게 둡니다.
- Claude와 Codex 판정은 별도 job으로 두어, 각 job에 자기 자격증명 하나만 있게 합니다.
- Claude도 Read 도구가 작업 디렉터리 밖(`/proc/self/environ` 등)을 읽지 못하는지 Q20에서 확인합니다.

### 4. PR을 병합까지 밀어 줄 주체가 없습니다

모두 fail-closed라 안전 문제는 아닙니다. 하지만 무인 세션 2개(Q19)를 돌리면 첫날부터 PR이 쌓입니다. "PR 준비 완료 이후"에 누가 무엇을 하는지가 정의되어 있지 않기 때문입니다.

- **뒤처진 브랜치**
  - "main 최신 필수"(47행)를 켜면, 다른 PR이 병합될 때마다 열린 PR이 모두 뒤처집니다. 자동 병합은 브랜치를 갱신해 주지 않습니다. 10.3절 절차 4는 충돌할 때만 다룹니다.
  - merge queue는 조직 소유 리포 전용으로 알고 있습니다. Q20의 이 항목은 "불가"로 닫으면 됩니다(686행).
  - 갱신 주체가 필요합니다. **GITHUB_TOKEN으로 갱신하면 `pull_request` 워크플로가 실행되지 않으므로** 봇 토큰을 써야 합니다.
  - 위험도 "높음" PR은 갱신할 때마다 제작자 승인이 무효가 됩니다(670행, 승인이 head SHA에 묶임). main이 바쁘면 승인 → 갱신 → 재승인이 반복됩니다. 제작자 승인도 patch-id에 묶는 것을 검토하세요.
- **계획 완료 커밋**
  - `plan-gate`는 계획 상태 `completed`를 요구하는데(667행), 그 커밋은 승인 뒤에 넣습니다(422행, 691행). 승인은 CI에서 비동기로 나오므로, 그 시점에 세션이 없으면 아무도 넣지 않습니다.
  - PR을 준비 완료로 바꿀 때 `completed`로 표시하고, 이후 수정은 진행 로그에만 덧붙이면 해결됩니다. 계획 전용 커밋 규칙이 이미 이것을 허용합니다.
- **2라운드 대응**
  - 선점 소유자가 `claude-code/<세션 식별자>`(387행)라서, 다음 세션은 "내가 선점한 활성 계획"(421행)에 해당하지 않습니다. 수정 요청을 받은 PR은 선점이 만료되는 24시간 동안 방치됩니다.
  - 소유를 세션이 아니라 고정된 작업 슬롯(예: `mac1-slot1`)에 묶고, 세션 시작 절차에 "내 슬롯의 열린 PR 확인(수정 요청, 뒤처짐, 검증 누락)"을 넣습니다.
- **Codex 검증 취소**
  - concurrency group(881행)은 실행 1개와 대기 1개만 둡니다. 새 대기가 들어오면 **기존 대기를 취소합니다**. PR이 몰리면 일부 PR에는 `review/codex`가 영영 기록되지 않습니다.
  - cron으로 "검증 상태가 없는 PR"을 찾아 다시 실행하는 정리 작업을 둡니다. 10.1절의 "재시도하며 병합을 보류"를 실제로 수행하는 주체도 이것이 됩니다.

## 보통

### 5. 파일럿 지표로는 검증 품질을 판정할 수 없습니다 (1062행)

- 브랜치가 main 최신이어야 병합되므로, 병합 후 main CI는 병합 전과 같은 검사입니다. 실패한다면 대부분 flaky 테스트 때문입니다. 버그 Issue를 쓸 사람도 거의 없습니다.
- 결국 5~10건에서 결함 0건이 나와도 품질이 좋다는 근거가 되지 않습니다. 그런데 4단계 완료 기준과 섀도 모드 재검토 조건(1274행)이 이 지표에 걸려 있습니다.

**제안**: 버그 심기 평가를 합니다. 알려진 결함(경계 조건, 권한 누락, 테스트 무력화 등)을 심은 PR로 검증자별 탐지율을 재고, 정상 PR로 오탐률도 잽니다. 12.4절 하네스 자체 테스트에 넣으면 사람 시간이 들지 않고, 섀도 모드 없이도 됩니다.

### 6. 선점 프로토콜에 구멍이 세 개 있습니다 (419~421행)

- 두 세션이 같은 커밋으로 `claim/42`를 push하면, 두 번째도 "Everything up-to-date"로 **성공합니다**. 세션 id를 담은 커밋을 push하거나, 이미 있으면 실패하는 ref 생성 API(`POST /git/refs`)를 씁니다.
- `blocked` 상태의 계획은 진행 로그를 갱신하지 않으므로 24시간 뒤 선점이 만료되고, 다른 세션이 같은 실패를 반복합니다. `needs-human`·`blocked` 상태는 만료와 작업 고르기 대상에서 뺍니다.
- 만료로 claim 브랜치가 지워진 뒤 원래 세션이 생존 확인 push를 하면 브랜치가 되살아납니다. `--force-with-lease=claim/42:<예상 SHA>`로 push하고, 실패하면 선점을 잃은 것으로 보고 멈추게 합니다.

### 7. 자동 revert가 해를 끼치거나 막힙니다 (696행)

- 병합 후 main CI 실패는 대부분 flaky라서, 바로 revert하면 정상 변경을 되돌리고 계획을 `active`로 돌려 일을 반복합니다. 5.2절처럼 같은 커밋에서 1회 재실행한 뒤에도 실패할 때만 revert합니다.
- revert PR은 계획 파일이 없어서 `plan-gate`에 걸립니다. `auth/**`를 되돌리는 revert PR은 경로별 위험도 표 때문에 `risk-gate`에도 걸립니다. `revert-check`를 통과한 PR의 `plan-gate`·`risk-gate`·`review-ledger` 처리 규칙을 명시합니다.

### 8. R5 테스트 실효성 검사가 오탐과 미탐을 냅니다 (227행)

- **미탐**: 새 기능의 테스트는 base에서 import·컴파일 오류로 "실패"하므로, 아무것도 확인하지 않는 테스트도 통과합니다.
- **오탐**: 기존 동작을 확인하는 테스트(특성화 테스트, 커버리지 보강)는 base에서도 통과하는 게 정상인데, 이 검사에 막힙니다. 지금 예외 목록(문서·설정·순수 리팩터)에도 없습니다.

**제안**: base에서 assertion 실패로 떨어질 때만 "실패"로 인정하고(테스트 리포터의 실패 유형으로 구분), 기존 동작 테스트는 예외로 둡니다. 근본적으로는 변경된 라인에 대한 뮤테이션 테스트가 더 정확합니다.

### 9. 격리 주석이 R4를 우회하는 통로가 됩니다 (249~256행)

- `tech-debt-tracker.md`는 보호 경로가 아닙니다. 그래서 기능 PR 안에서 TD 항목을 새로 추가하고 `until=2099-12-31`로 격리하면, 결정적으로 실패하는 테스트를 건너뛸 수 있습니다. 검증자가 놓치면 그대로 병합됩니다.

**제안**: 아래 조건을 모두 R4 검사로 기계 확인합니다.
- 격리는 다른 변경이 없는 PR에서만 허용합니다.
- `until`은 최대 30일로 제한합니다.
- TD 항목은 main에 이미 있어야 합니다.
- 동시에 격리할 수 있는 테스트 수에 상한을 둡니다.

### 10. E5에서 SSH 키와 git 자격증명이 빠졌습니다 (38행)

- E5는 `gh` 토큰만 언급합니다. 제작자의 SSH 키(`~/.ssh`)나 키체인에 저장된 git HTTPS 자격증명(`git credential fill`로 꺼낼 수 있음)이 있으면, 같은 OS 사용자로 실행되는 에이전트가 제작자 신원으로 push할 수 있습니다.
- 이렇게 되면 운영 단계에서 봇의 `workflows` 권한을 회수해도 워크플로 파일을 올릴 수 있습니다.

**제안**: E5에 "제작자 GitHub SSH 키와 git 자격증명 도우미 항목도 이 Mac에 두지 않는다"를 추가하고, R20의 L1 차단 목록에 `git credential`과 `credential.*` 설정 변경을 넣습니다.

### 11. 단계별로 보면 "차단" 표기가 실제와 다릅니다

- L0는 4단계(1120행)에 들어옵니다. 그런데 3단계에서 필수인 `web-verify`의 외부 도메인 차단(781행), 14.4절의 네트워크 제한, 3번의 유출 차단이 모두 L0에 기댑니다.

**제안**
- L0 중 네트워크 허용 목록만 1단계로 당깁니다. Claude Code 샌드박스의 네트워크 설정과 Codex `workspace-write`(기본이 네트워크 차단)를 쓰면 비용이 작습니다.
- 5.1절 규칙 표에 "도입 단계" 열을 추가해, 단계마다 실제 보장 수준이 보이게 합니다. 이런 불일치가 반복되는 근본 원인이 이것입니다.

### 12. 0.2절의 승인 관련 설정 두 개를 확인해야 합니다 (48~49행)

- 두 설정 모두 "PR 필수"의 하위 옵션이며, 필수 승인 수가 1 이상일 때를 전제로 합니다. 이 설계는 필수 승인 수가 0입니다(제작자 승인은 `risk-gate`가 확인).
- 특히 "Require approval of the most recent reviewable push"는 승인 수가 0이어도 다른 사람의 승인 1개를 요구하도록 동작할 수 있습니다. 그러면 모든 자동 병합이 막힙니다.
- 결국 아무 효과가 없거나 전부 막거나 둘 중 하나입니다. Q20에서 확인하고, 효과가 없으면 문서에서 빼서 `risk-gate`가 제작자 승인의 유일한 근거임을 분명히 합니다.

## 선택

### 13. `related_code` 판정도 `last_verified`와 같은 약점이 있습니다 (357행)

- 문서를 한 줄만 고쳐도 "검토 필요"가 풀립니다.
- 실질적인 판정은 4.4절 DoD("관련 문서를 갱신했거나 갱신이 필요 없는 이유를 적었다")를 검증자가 확인하는 것입니다. 판정 근거를 그쪽에 두고, 이 방식은 보조로 둡니다.

### 14. 검증자의 지적은 작성 에이전트에게 지시문이 됩니다

- 14.6절은 검증자로 들어가는 외부 입력만 다룹니다. 반대 방향도 막아야 합니다.
- 지적이 보호 경로, 자격증명, 네트워크 설정 변경을 요구하면 따르지 않고 에스컬레이션한다고 적어 둡니다.

### 15. 작은 동작 변경에도 LLM이 4회 이상 실행됩니다

- 동작이 바뀌면 "중" 규모가 되고(189행), 계획 검증 A+B와 코드 검증 A+B를 거칩니다. 수정 라운드가 생기면 더 늘어나고, Codex는 직렬로 돕니다.
- 구독 한도(Q12)가 먼저 바닥날 가능성이 큽니다. 계획 교차 검증을 대규모나 위험도 높음 작업에만 두는 안을 파일럿에서 비교군으로 둘 만합니다.

### 16. L0 쓰기 범위와 git worktree가 충돌합니다

- worktree의 커밋은 main 체크아웃 쪽 `.git/worktrees/<id>`와 공용 `.git/objects`에 써야 합니다. 그래서 쓰기 범위를 worktree 경로로만 묶으면 커밋이 안 됩니다.
- 공용 git 디렉터리를 허용 경로에 넣어야 하는데, 그러면 `attempts.jsonl`(424행)도 에이전트가 쓸 수 있는 범위에 들어갑니다. Q4에 함께 적어 둡니다.

### 17. `AGENTS.md` 줄 수 상한을 doc-lint로 강제합니다

- 원문이 첫 번째 실패로 꼽은 것이 이 파일의 비대화입니다. B2를 기계로 확인하는 장치가 됩니다(예: 120줄).
