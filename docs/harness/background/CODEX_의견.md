# 하네스 엔지니어링 설계 평가

> 대상: `하네스엔지니어링.md` (v0.3)
> 참고: `openai.md` — OpenAI의 하네스 엔지니어링 글
> 평가일: 2026-11-10

## 총평

설계 방향은 탄탄하다. OpenAI 글의 핵심인 **짧은 진입 문서, 리포지터리를 기록 시스템으로 쓰기, 아키텍처 경계의 기계적 강제, 에이전트가 직접 검증할 수 있는 환경, 정기적인 드리프트 정리**를 구체적인 요구사항으로 발전시켰다. 특히 작업 기록과 앱 런타임 관측성을 구분한 점(11절), 위험한 DB·운영 작업을 명령 차단만이 아니라 권한 제한으로 막으려는 방향(14절)이 좋다.

다만 현재 문서는 하네스 설계서이면서 **엄격한 자율 개발 조직의 운영 규정**에 가깝다. OpenAI 글에서 강조한 빠른 처리량과 적은 병합 차단 기준보다 더 많은 절차를 기본값으로 두고 있다. 이대로 구현하면 작은 팀에서는 자동화 비용과 리뷰 대기 시간이 병목이 될 수 있다.

**평가:** 설계 방향은 좋지만, 구현 전에 강제 수준과 적용 범위를 조정할 필요가 있는 초안이다.

## 우선 수정할 항목

### 1. 강제 가능성과 정책을 구분한다

“모든 규칙은 기계적으로 강제한다”는 목표는 좋지만, CI는 PR 결과물을 검사할 수 있을 뿐 에이전트가 실행하는 모든 셸 명령을 통제할 수는 없다. Git 훅도 `--no-verify` 등으로 우회될 수 있다.

R13·R14를 비롯한 규칙마다 아래 수단을 구분해 표시하는 것이 좋다.

- **권한으로 차단:** 자격증명, OS 권한, 네트워크 경계로 실행 자체를 막음
- **결과물 검사:** CI가 코드·설정·마이그레이션 등을 검사함
- **절차상 요구:** 에이전트가 따르도록 지침을 주고 리뷰에서 확인함

이렇게 하면 실제로 보장할 수 있는 범위와 운영상 기대를 혼동하지 않는다.

### 2. 보편 규칙과 프로젝트별 규칙을 나눈다

모든 작업에 worktree, 계획, 2인 교차 검증, 전체 `check`, PR 크기 제한을 적용하면 큰 변경에는 유용하지만, 작은 저장소나 단순 수정에도 비용이 든다. 4.3절의 작업 규모 구분을 기준으로 게이트를 달리 적용하거나, 작은 웹 프로젝트 하나에서 시범 운영한 뒤 범용 코어에 올릴 규칙을 결정하는 편이 현실적이다.

### 3. 리뷰 라운드의 ‘지적 동결’을 안전하게 조정한다

10.2절의 2라운드 이후 규칙은 수렴에 도움이 되지만, 바뀌지 않은 코드에서 뒤늦게 발견한 P1 결함을 놓칠 수 있다. 기존 코드를 매 라운드 전면 재검토하지 않되, 새로 발견한 **근거 있는 P1 결함은 원장에 추가하고 병합을 차단할 수 있게** 하는 편이 안전하다.

### 4. 자동 revert 적용 범위를 제한한다

병합 후 CI 실패 시 자동 revert PR을 만드는 규칙은 코드 변경에는 쓸 수 있지만, 데이터나 외부 시스템에 영향을 준 변경은 Git revert만으로 복구되지 않는다. 자동 복구는 코드만 되돌릴 수 있는 변경으로 제한하고, 그 외에는 원인과 영향 범위를 평가해 에스컬레이션하도록 나누는 것이 좋다.

### 5. 실패 횟수의 계산 단위를 구체화한다

3회 방법 전환·5회 중단 규칙은 반복 작업을 멈추는 장점이 있지만, 서로 다른 검사 실패를 한 목표의 누적 횟수에 어떻게 더하는지 불명확하다. 실패를 **목표 + 검사 또는 지적 ID** 단위로 세고, 환경 장애·기존 실패·flaky 재실행은 별도 처리한다고 정하면 불필요한 중단을 줄일 수 있다.

## 추가로 다듬을 점

- **TDD:** 동작 코드와 테스트 파일이 함께 바뀌었는지만으로 테스트 우선 작성이나 테스트의 의미를 입증할 수 없다. PR에 실패 재현 결과를 남기는 요구와 자동 검사 가능한 항목을 구분한다.
- **PR 400줄 제한:** 초기 가설로 두는 편이 좋다. 생성 파일·테스트·문서 제외 기준에 따라 규모가 왜곡될 수 있고, 큰 기능을 억지로 나누면 검토가 더 어려워질 수 있다. 처음에는 경고로 운영하고 리뷰 라운드와 리드타임을 본 뒤 차단 기준으로 바꿀지 결정한다.
- **문서 최신성:** `last_verified` 기한 초과를 CI 실패로 만들려면 문서 종류별 검증 주기와 예외가 필요하다. 자동 생성 문서, 정책 문서, 활성 제품 문서를 같은 주기로 검사하지 않도록 분류한다.
- **자동 병합의 신뢰 경계:** 사람 승인 없이 교차 검증 두 건으로 자동 병합하려면, 병합 자격증명의 권한, 보호 설정 변경 권한, 검증자 승인 확인 방법을 설계에 포함한다.

## 권장 다음 단계

19절의 로드맵을 한 번에 전부 구현하기보다, 먼저 **계획·문서 구조·표준 명령·기본 CI**를 적용해 웹 프로젝트 하나에서 시범 운영한다. 실제 작업을 몇 건 처리한 뒤 계획 의무 범위, 교차 검증의 실효성, 리뷰 라운드, 실패 횟수, 자동 병합 범위를 조정하면 과잉 설계를 줄이면서 핵심 원칙을 유지할 수 있다.

## 결론

OpenAI 글의 아이디어를 잘 구조화했고, 위험 작업 통제와 리뷰 수렴까지 고민한 점이 강점이다. 다음 개정에서 우선 명확히 할 것은 세 가지다.

1. 무엇이 실제로 강제 가능한가
2. 작업 규모에 따라 어떤 절차가 필요한가
3. 자동 복구가 안전한 변경의 범위는 어디까지인가

## 총평

초기 의견에서 지적한 강제 수준, 리뷰 수렴, 위험 작업, 작업 접수와 신뢰 경계를 상당 부분 구체화했다. OpenAI 글을 그대로 복제하지 않고, 1~2인 운영과 자동 병합이라는 조건에서 차이를 설명한 점(3.1절)이 좋다. 보장 수준 구분(5절), 위험도별 검증(10.1절), 하네스 자체 테스트(12.4절), 구축·운영 단계 분리(10.4절)가 강점이다.

## 우선 수정할 항목

### 1. 자동 병합 전에 파일럿을 진행한다

19절은 2단계에서 자동 병합을 켠 뒤 3단계에서 실제 작업 5~10건을 파일럿으로 수행한다. 파일럿 동안은 검사와 교차 검증을 돌리되 병합을 사람이 확인하고, 결과를 본 뒤 저위험 PR부터 자동 병합을 활성화하는 순서가 안전하다. 5~10건은 파이프라인 작동과 운영 적합성을 보는 데 유용하지만, 자동 병합의 안전성을 확증하기에는 적은 표본이다. 검증 누락·오탐, 병합 후 결함, PR당 대기 시간과 사용량을 완료 기준에 포함한다.

### 2. R1이 보장하는 범위를 정확히 쓴다

`plan-gate`는 계획 파일과 필수 항목의 존재를 확인한다(5.1절 R1, 10.3절). PR 최종 상태만 검사해서는 계획이 코드 수정 전에 작성됐는지 알 수 없다. 현재 검사로 확인되는 것은 완성된 계획이 PR에 포함됐다는 사실이다. 이 범위로 규칙을 표현하거나, 계획 전용 커밋이 코드 변경보다 앞서도록 확인하는 절차를 추가한다. 순서를 완전히 증명할 수 없다면 R1을 검출이 아니라 절차 수준으로 분류하는 편이 정확하다. TDD 검증의 한계를 밝힌 R5가 좋은 기준이다.

### 3. 모델 리뷰를 독립적인 안전 보증으로 간주하지 않는다

서로 다른 도구의 리뷰는 관점을 넓히지만, 같은 체크리스트와 PR 내용을 보는 두 모델이 독립적인 검증을 보장하지는 않는다. 특히 2라운드 이후 바뀌지 않은 코드의 새 P1을 실패 테스트로 재현해야만 인정하면, 재현 테스트를 만들기 어려운 보안·정적 분석 지적을 놓칠 수 있다. 구체적인 근거가 있는 심각한 지적은 테스트가 없어도 다시 열 수 있게 하고, 파일럿 중 일부 PR은 사람이 확인해 모델 리뷰의 놓침과 오탐을 기록한다.

### 4. 초기 구현 범위를 파일럿에서 줄인다

현재 코어에는 GitHub, GitHub Actions, Claude Code, Codex를 전제로 한 운영 요소가 많다. 언어·엔진 중립성뿐 아니라 지원할 서비스 조합과 제외 범위를 명시하면 “범용”의 기대를 맞출 수 있다. 1~2인 운영에서는 Issue, 모든 작업의 계획 파일, worktree, 교차 검증, 전체 검사, 리뷰 원장과 정기 작업이 비용이 될 수 있으므로, 기본 계획·표준 명령·CI·브랜치 보호부터 실제 웹 프로젝트에서 확인한 뒤 확장한다.

- **검사 결과 캐시:** `check`를 작업 트리 해시로만 캐시하면 런타임·도구 버전·플랫폼이 바뀐 경우 오래된 결과를 재사용할 수 있다. 프로파일·런타임·플랫폼·명령 버전을 키에 포함하거나 무효화 조건을 둔다(6절).

- **파일럿 판정:** 리뷰 라운드 수뿐 아니라 실패한 병합, 사람이 되돌린 AI 판정, 검증 사용량·대기 시간을 포함해 자동화 확대 기준을 정한다.

## 총평

보안 방향은 타당하다. 운영 자격증명과 에이전트를 분리하고, 파괴적 DB 작업은 명령 차단만이 아니라 권한으로 막으며, 비공개 개인 리포에서 push 보호를 쓸 수 없다는 점도 문서에 드러냈다. 다만 실제 보안은 지침보다 실행 환경과 자격증명 격리에 달려 있다. 자동 병합 전에 아래 두 가지를 우선 해결해야 한다.

## 최우선 개선 항목

### 1. 실제 `.env`를 에이전트가 읽을 수 있는 worktree에 링크하지 않는다

14.2절은 비밀 파일을 리포 밖에 두고 worktree에 링크한다. OS 샌드박스가 심볼릭 링크의 실제 대상까지 차단하는지 확인해야 한다. 파일이 리포 밖에 있다는 사실만으로는 에이전트의 접근을 막지 못한다.

실제 키 대신 가짜 값이나 범위가 제한된 테스트 키를 사용하고, 실제 비밀정보는 에이전트가 읽을 수 있는 worktree와 프로세스 환경에서 분리하는 구성을 권한다. `.gitignore`와 훅은 보조 수단이다. L0가 파일 접근을 실제로 막지 못한다면 R10의 “push 전 차단”은 성립하지 않는다.

현재 GitHub 개인 Pro 비공개 리포에서 서버 측 push protection을 쓸 수 없다는 전제는 공식 문서와 부합한다. 조직 소유 비공개 리포에는 Team 또는 Enterprise와 Secret Protection이 필요하다. 따라서 현 구성의 보장은 “로컬 예방 + push 후 탐지·키 교체”로 정확히 표현하는 편이 좋다. [GitHub 시크릿 검사 적용 범위](https://docs.github.com/en/code-security/reference/secret-security/secret-scanning-scope)

### 2. AI 검증자와 지속 보존되는 Codex 인증 파일을 격리한다

10.4절은 `pull_request_target`에서 PR 코드를 실행하지 않게 하지만, 검증 모델은 PR diff와 파일을 읽는다. 악의적인 내용이 모델의 도구 사용을 유도할 수 있다. 도구가 읽기 전용이어도 인증 파일을 읽거나 결과에 포함시키는 것을 막지는 않는다.

13.3절은 Codex 인증 파일을 상시 self-hosted 러너에 보존한다. 특히 제작자의 일상용 Mac을 파일럿 러너로 쓰면 인증정보와 다른 개인 파일이 같은 사용자 환경에 놓일 수 있다. 검증을 실행마다 폐기하는 격리 환경에서 돌리고, 모델 검증 작업과 GitHub 상태 기록 작업을 분리한다. 모델 작업에는 GitHub 쓰기 자격증명을 주지 않고, 별도 게시 작업만 최소 권한의 GitHub App으로 상태를 기록하게 한다. 같은 리포의 PR도 신뢰할 수 있는 입력으로 간주하지 않는다.

GitHub는 `pull_request_target`에서 신뢰할 수 없는 코드를 실행하지 말고, self-hosted runner를 격리·일회용으로 구성하라고 권고한다. [GitHub의 `pull_request_target` 보안 지침](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target), [GitHub Actions 안전한 사용](https://docs.github.com/en/actions/reference/security/secure-use)

### 3. 보안 제어 경로는 구축 단계부터 제작자 승인을 요구한다

10.4절의 구축 단계에서는 `.github/`, 스크립트, 샌드박스와 검사 규칙 변경도 AI 검증 후 자동 병합될 수 있다. 이 경로의 변경을 놓치면 이후 검증 체계 자체가 약해진다. 적어도 워크플로 권한, 자격증명 처리, 샌드박스, 검증 프롬프트, 브랜치 보호를 바꾸는 PR은 운영 단계 전환 전에도 제작자가 승인하게 하라.

브랜치 보호의 관리자 우회 금지는 봇의 우회를 막는 설정이다. 저장소 관리자는 설정을 변경할 수 있으므로, 제작자 계정의 강한 MFA, 보호 설정 변경 알림, 설정 드리프트 점검도 전제에 포함하는 것이 좋다.

## 추가 강화 권고

- **Actions 권한과 의존성:** 워크플로마다 `GITHUB_TOKEN` 권한을 명시적으로 최소화하고, 액션은 검증된 전체 커밋 SHA로 고정한다. PR 코드가 실행되는 `check` 작업에 쓰기 가능한 토큰이나 비밀정보를 주지 않는다. [GitHub Actions 보안 지침](https://docs.github.com/en/actions/how-tos/secure-your-work)
- **외부 입력과 네트워크:** `accepted` 라벨은 작업 접수만 뜻하게 하고, 외부 이슈·PR diff·웹 페이지·패키지의 지시문은 계속 신뢰하지 않는다. 브라우저뿐 아니라 로컬 앱과 테스트 프로세스에도 egress 제한을 적용하고, 운영 API와 클라우드 메타데이터 주소에 접근하지 못하게 한다.
- **DB 위험 분류:** SQL 패턴 검사만으로 파괴적 변경을 모두 찾아낼 수 없다. 마이그레이션·데이터 스크립트는 위험도가 높은 변경으로 취급하고, 분류 오류나 미확인 파일 형식은 fail-closed로 처리한다.
- **유출 사고 대응:** 키 폐기·재발급 외에 해당 자격증명의 사용 로그 조사, 러너 폐기·재생성, 필요 시 Git 이력 정리까지 runbook에 기록한다. CI에서 발견된 시크릿은 이미 원격에 올라갔다는 전제로 대응한다.
- **공급망:** 새 패키지의 게시 기간·라이선스·ADR 확인만으로 악성 패키지를 막지는 못한다. lockfile과 레지스트리를 고정하고, 의존성 설치·테스트를 비밀정보 없는 일회용 러너에서 수행한다.

## 결론

보안 원칙은 잘 세워졌지만, 두 경계가 구현으로 증명되기 전에는 자동 병합 준비가 끝난 것으로 보기 어렵다. 우선 **worktree에서 실제 `.env` 접근 차단 확인**, **AI 검증자의 인증정보 격리**, **보안 제어 파일 변경 승인**을 확정하라. 그다음 최소 권한의 Actions, 외부 입력의 네트워크 격리, 시크릿 사고 대응 절차를 보완하는 순서가 적절하다.
