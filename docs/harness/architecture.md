# 하네스 코드 구조

하네스 코드는 모두 `scripts/` 아래 TypeScript이며 Node 22.18+가 빌드 없이 바로 실행한다([ADR-0001](../decisions/ADR-0001-script-language.md)). 런타임 의존성은 없고 `node:` 내장 모듈만 쓴다.

## 레이어

의존은 위에서 아래로만 흐른다. `scripts/selftest/`(하네스 자체 테스트)는 이 레이어 밖에 있다: 하네스의 내부 모듈을 import하지 않고 CLI와 훅을 프로세스로만 부른다.

```
진입점      scripts/harness.ts (CLI)          scripts/hooks/guard.ts (L1 훅), session.ts (세션 훅)
              │                                     │
명령·runner  commands/  (표준 명령, check, new-task, complete-step, pr-ready, pr-state, ops-check, metrics, start, init)
             runner/    (run: 루프, next: 우선순위·새 Issue 작성자 확인, agents: 세션, prompt)
             metrics/   (metrics 명령의 자료 읽기·지표 계산·렌더. GitHub은 읽기만 한다)
             ci/        (gates·judge-* 워크플로: 기계 판정 결과 조립, 검증자 계획·입력·유출 검사, 결과 검사·커밋 상태 기록)
             verify/    (verify 표준 명령의 웹 구현: 거부 프록시, dev 띄우기, 시나리오 실행기, 판정, 프로세스 정리와 자손 추적, 증거 요약. Playwright 설정과 fixture는 profiles/web/verify/)
              │
게이트       gates/     (plan-gate, doc-lint, bypass-scan, secret-scan, test-effect)   hooks/rules.ts, hooks/shell.ts
              │
라이브러리   lib/       (exec, git, config, plan, attempts, github, util)
```

(1) 부모·자식 관계: 도는 동안 프로세스 목록에서 dev와 실행기의 자손을 주기적으로 찾아 기억한다. (2) 표식: `web.ts`는 dev와 실행기에 그 실행만의 환경 변수(`HARNESS_VERIFY_RUN=<난수>`)를 준다. 자손이 물려받으므로 정리할 때 그 표식을 가진 프로세스를 부모와 무관하게 찾는다. 목록을 읽는 사이에 브라우저가 뜨고 실행기가 죽어 한 번도 보지 못한 프로세스도 이것으로 찾는다. 프로세스는 번호가 아니라 인스턴스(번호와 시작 시각)로 기억한다: 번호는 프로세스가 끝나면 다른 프로세스가 다시 받을 수 있다. 신호를 보내기 직전에 그 번호의 시작 시각을 다시 읽어 같을 때만 보낸다(무관한 프로세스를 끝내지 않는다). 표식에는 있고 목록에는 아직 없는 번호는 어느 프로세스인지 모르므로 신호는 보내지 않고 남은 것으로만 센다(다음에 읽은 목록에 나오면 대상이 된다). 읽는 수단은 운영체제마다 하나다: Linux는 `/proc`(`<pid>/stat`, `<pid>/environ`), macOS는 `ps`(`-o pid=,ppid=,pgid=,stat=,lstart=`와 `-E`). 정리는 그룹과 함께 찾은 프로세스들에도 SIGTERM(2초 뒤 SIGKILL)을 보내고, 기다리는 동안 새로 찾은 프로세스에도 보내며, 모두 사라진 것을 이어서 두 번 확인한 뒤 돌아간다. 신호를 보낸 바로 뒤에는 돌아가지 않고 그것이 끝나는 것을 본다(기한에 더해 최대 3초). 도중에 목록을 읽지 못해도 멈추지 않고 목록에서 확인했던 프로세스에는 SIGKILL까지 보낸다. 끝내 목록이나 표식을 읽지 못하면 남은 것이 없는지 확인하지 못한 것이라 `verify`가 실패한다. `web.ts`의 명령행은 표준 명령 실행기가 넘기는 신호(SIGTERM·SIGINT·SIGHUP, `lib/exec.ts`의 `FORWARDED`)를 모두 받아 같은 정리 경로로 들어간다. `fixture.ts`: 시나리오가 쓰는 `test`. 요청을 막지 않고 본다. 무엇이 앱 주소 밖인지, 의도한 실패 선언이 어떤 항목에 맞는지, 관찰 기록에 무엇을 남기는지는 Playwright를 쓰지 않는 `observe.ts`에 있고 이 리포의 테스트(`scripts/test/verify-observe.test.ts`)가 직접 본다(정규식 선언은 플래그를 그대로 둔 새 정규식으로 항목마다 처음 위치부터 본다). 콘솔 에러·잡히지 않은 예외·실패한 요청·앱 주소 밖으로 가려던 요청과 웹소켓(`blocked`)을 적어 `harness-verify` 첨부로 붙인다. 의도한 실패 선언(`allowConsoleError`, `allowFailedRequest`)은 분류별로 따로 빼고 `blocked`는 빼지 못한다. 실제 Playwright로 사례별로 돌린 기록은 `lab/pilot-prep/`에 있다 |

- `harness.config.json`: 단계(`stage`), 표준 명령 정의, 한도(Q19), 보호 경로, 에이전트 실행 인자. 보호 경로다.
- `profiles/<이름>/profile.json`: 프로파일이 채우는 값. `node scripts/harness.ts init --profile web`이 설정에 병합한다. 코어 코드는 프로파일을 몰라도 된다(S5).

## 테스트

`scripts/test/*.test.ts` (node:test). 임시 git 리포 + 로컬 bare 원격 + 가짜 GitHub(`HARNESS_FAKE_GH`) + 가짜 에이전트(`HARNESS_FAKE_AGENT`, `scripts/selftest/fake-agent.ts`)로 runner 전체 흐름까지 검사한다. 테스트 안에서 `node --test`를 자식 프로세스로 띄울 때는 환경 변수 `NODE_TEST_CONTEXT`를 빼고 띄운다. 넘어가면 자식이 테스트 파일을 실행하지 않고 종료 코드 0으로 끝난다.

`scripts/selftest/` (하네스 자체 테스트, 설계서 12.4절). `run.ts`가 대상 하네스(`--harness`, 기본은 이 리포)를 임시 샘플 리포에 복사하고 `scenarios/*.ts`를 파일 이름순으로 돌린다. 시나리오는 `ctx.cli`(CLI)와 `ctx.hook`(L1 훅)만 부르고, 규칙이 막아야 할 것을 막는지와 대조군이 통과하는지를 종료 코드로 확인한다. runner 시나리오는 `ctx.agent`로 가짜 에이전트(`fake-agent.ts`, 실행기 쪽 파일)의 동작을 정하고 CLI로 `run`을 띄운 뒤, `ctx.github`로 가짜 GitHub 상태 파일을 읽고 고친다(CI가 남길 체크·원장 댓글). CI 명령의 REST 조회는 `ctx.api`가 띄우는 읽기 전용 로컬 서버(`api-stub.ts`)가 답한다. 새 시나리오는 파일을 더하면 들어간다(목록 파일 없음). `scripts/test/selftest.test.ts`가 `check`에서 이 리포와 약화된 사본을 시험한다. 보호 경로를 바꾼 PR에서는 `gates` 워크플로의 `selftest` job이 main의 실행기로 PR의 하네스를 시험한다(`--harness pr`). 실제 세션 시나리오는 `live.ts`(`runLive`)와 `live/*.ts`다: `node scripts/harness.ts self-test --live [--runs <N>] [--only <id,id>] [--out <파일>]`이 대상 하네스 설정의 `agents.claude`로 샘플 리포에서 세션을 띄우고, PATH 앞에 둔 가짜 `gh`·`psql`의 호출 기록으로 판정해 시나리오별 통과 수를 낸다. 구독 인증이 필요해 손으로만 실행하고 `check`·CI에서는 돌지 않는다(`run.ts`는 `scenarios/`만 읽는다).
