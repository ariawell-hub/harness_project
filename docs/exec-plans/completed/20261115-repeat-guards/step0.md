# Step 0: rules-doc

## 읽어야 할 파일

- `AGENTS.md` (작업 루프 6번, "판단이 필요하면" 항목, 세션 시작 절차)
- `docs/harness/workflow.md` 1절(위험도), 4절(`check` 결과는 종료 코드로), 5절(PR), 7절(에스컬레이션)
- 이 계획의 의사결정 로그(위험도 문구는 기준을 좁히지 않는다)

## 작업

1. `AGENTS.md` 작업 루프 6번(PR) 아래에 더한다.
   - 위험도 높음 PR은 초안으로 올리고, 조건(완료 처리 push, 이 PR에 넣을 기록 완료, `origin/main` 병합 최신, `check` 통과, 필요한 제작자 작업 반영)을 채운 뒤 초안을 해제하며 승인을 요청한다.
   - 제작자 작업(App ID, 시크릿, 필수 체크 등록)은 한 번에 모아 요청하고, 순서·확인 방법·절차 문서 링크·넣을 값의 형식을 적는다.
2. `AGENTS.md`의 "판단이 필요하면" 항목을 보강한다.
   - 추천안이 있으면 묻지 않고 진행한다. 물을 때는 절차서 7절 "반드시 묻는다"의 어느 항목인지 적는다.
   - 멈추거나 기다릴 때는 무엇을 기다리는지, 누가 풀어야 하는지(봇·제작자·CI), 그동안 무엇을 하는지를 알린다.
3. `AGENTS.md`에 "명령 작성 규칙"을 더한다: `check`·`test` 출력을 파이프로 자르지 않는다, 검사와 완료 처리·push·PR 생성은 `&&`로만 잇는다, 대기는 `until` 반복, 임시 폴더는 새로 만들고 변수 경로를 재귀 삭제하지 않는다, 명령에 `GH_TOKEN=`을 붙이지 않는다.
4. `docs/harness/workflow.md`에 같은 내용을 절차 수준으로 적는다: 1절에 위험도를 붙이는 범위(기준에 해당하는 작업에만, 애매하면 high, 제작자 결정 2026-11-15), 5절에 승인 요청 전 조건과 제작자 작업 요청 형식, 7절에 대기 상태 보고.
5. `AGENTS.md`는 지도다. 규칙은 한두 줄로 적고 세부는 절차서로 링크한다.

## Acceptance Criteria

```bash
grep -q "명령 작성 규칙" AGENTS.md
grep -q "초안" AGENTS.md
grep -q "승인 요청 전" docs/harness/workflow.md
node scripts/harness.ts doc-lint
```

## 금지사항

- 위험도 기준(보안·인증·마이그레이션·데이터 스크립트)을 좁히거나 지우지 마라. 이유: 사람 확인이 줄어 제작자 조건에 어긋난다.
- 절대 규칙(R1~R20) 문구를 바꾸지 마라. 이유: 이 step은 규칙을 더할 뿐이다.
- 코드(`scripts/`, `.claude/`)를 고치지 마라. 이유: step1 이후의 범위다.
