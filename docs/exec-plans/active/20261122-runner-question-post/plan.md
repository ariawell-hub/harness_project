# runner의 질문 댓글 게시가 실패해도 질문이 올린 것으로 기록된다(길이 상한 초과 포함)

## 목표와 수용 기준

runner는 세션이 계획의 "열린 질문"에 남긴 질문을 Issue 댓글로 올리고 답을 받을 때까지 그 계획을 멈춘다(`scripts/runner/run.ts`의 `askQuestions`, 설계서 4.5절). 지금은 계획을 `blocked`로 바꾸고 질문 제목을 "올린 질문"(`reported`)에 적은 **뒤에** 라벨과 댓글을 올리고, 올리지 못하면 경고만 남긴다. 그러면 제작자는 질문을 받지 못했는데 runner는 올린 것으로 기억하고 답을 기다린다. 같은 질문은 다시 올리지 않으므로 그 질문은 사라진다. 올리지 못하는 원인에는 GitHub의 댓글 길이 상한(65,536자)도 있다: 질문의 글을 코드 블록에 넣으면서(#198) 글 안의 가장 긴 백틱 줄보다 긴 펜스를 양쪽에 붙이므로 본문이 그만큼 길어지고, 올리기 전에 길이를 보는 곳이 없다(Issue #211. PR #203 판정의 F4).

수용 기준:

1. 질문이 제작자에게 전달된 것을 확인한 뒤에만 "올린 질문"으로 적는다. 전달은 Issue에 `needs-human` 라벨을 붙이고 댓글 하나를 올린 것이다(테스트).
2. 질문 댓글의 본문이 길이 상한을 넘으면 그 본문을 올리려 하지 않고, 질문의 글 대신 **계획 파일의 위치를 알리는 짧은 댓글**(안내 댓글)을 올린다. 질문 댓글의 게시가 실패했을 때도 안내 댓글을 올려 본다. 안내 댓글에는 세션이 쓴 글이 들어가지 않는다. 안내 댓글은 멈춘 계획이 push된 뒤에만 올린다(제작자가 그 브랜치에서 질문을 읽어야 한다)(테스트).
3. 둘 다 올리지 못하면 계획은 멈춘 채로 두고 "올리지 못한 질문이 있다"고 적는다. runner는 주기마다 다시 올려 보고, 올리지 못한 질문이 남아 있는 동안에는 "사람의 답을 기다린다"로 멈추지 않는다: 환경 장애로 보고 기다렸다가 다시 하며, 기다린 시간이 상한(`limits.usageLimitMaxWaitMin`)을 넘으면 `usage-limit`으로 멈춘다(지금의 환경 장애 처리와 같다)(테스트).
4. 올리지 못한 채로 제작자의 댓글이 달리면(질문을 보지 못하고 단 댓글) 지금처럼 답으로 받아 이어 가되, 그 질문은 "올린 질문"이 아니므로 세션 뒤에도 열린 질문에 남아 있으면 다시 올린다(테스트).
5. 게시가 성공하는 경우의 동작은 그대로다: 댓글의 글, 한 번만 올리는 것, 계획을 멈추고 push하는 것, 답을 받은 뒤의 흐름. 기존 runner 테스트가 단언을 고치지 않고 통과한다(테스트).
6. 설계서 4.5절에 올리지 못했을 때의 처리가 적힌다. `node scripts/harness.ts check`와 `node scripts/harness.ts self-test` 통과.

## 의사결정 로그

- 결정: 계획을 멈추는 것(`blocked`, push)은 지금처럼 게시보다 먼저 하고, "올린 질문"의 기록만 전달을 확인한 뒤로 옮긴다. 올리지 못하면 질문 상태에 `unposted`를 적어 주기마다 다시 올린다. / 이유: 멈추지 않고 실패로 돌려주면 다음 주기에 계획 작성 세션이나 step 세션이 다시 돈다(게시가 실패할 때마다 세션 하나가 든다). 멈춘 채로 게시만 다시 하면 드는 것이 API 호출 둘뿐이다. / 버린 대안: 게시를 먼저 하고 실패하면 계획을 멈추지 않는다(세션이 다시 돈다. step 세션은 작업 트리를 바꾼다).
- 결정: 다시 올릴 때 질문은 저장해 두지 않고 계획 파일에서 다시 읽는다(열린 질문 가운데 `reported`에 없는 것). / 이유: 멈춘 계획은 바뀌지 않으므로 같은 질문이 나온다. 저장하는 값이 표시 하나(`unposted`)로 준다.
- 결정: 길이 상한을 넘는 질문은 나눠 올리지 않고 안내 댓글을 올린다. / 이유: "범위 / 비범위"에 적었다. / 버린 대안: 여러 댓글로 나눈다, 글을 잘라 올린다(잘린 질문에 답하게 된다).
- 결정: 질문 댓글의 게시가 실패했을 때도(길이가 아닌 이유) 바로 안내 댓글을 올려 본다. / 이유: 본문의 내용 때문에 거부된 것이면(GitHub의 검증 오류) 다시 올려도 같은 결과다. 안내 댓글은 runner가 쓴 짧은 글이라 같은 이유로 거부되지 않는다. 네트워크 장애라면 안내 댓글도 실패하고 다음 주기에 처음부터 다시 한다. / 대가: 일시적인 실패 뒤에 안내 댓글만 성공하면 제작자는 질문의 글 대신 위치를 받는다(계획 파일을 열어 읽어야 한다).
- 결정: 길이는 문자열의 길이(UTF-16 단위)로 잰다. / 이유: GitHub이 세는 글자 수보다 같거나 크다(상한 아래의 본문을 안내 댓글로 돌리는 쪽으로만 틀린다). `scripts/ci/ledger-store.ts`의 원장 본문 검사와 같은 방식이다.
- 결정: 올리지 못한 질문이 남은 채로 할 일이 없으면 `human`으로 멈추지 않고 환경 장애 대기로 돈다. / 이유: `human`으로 멈추면 runner가 끝나고, 제작자는 질문을 받지 못했으므로 아무도 움직이지 않는다. 환경 장애 대기는 상한이 있고, 상한을 넘어 멈출 때의 알림(`usage-limit`)이 이미 있다.
