# ADR-0008 F2: selftest job을 1분 안에 끝낸다(시나리오를 나란히 돌린다)

## 목표와 수용 기준

ADR-0008 묶음 "호스팅 유지"의 네 번째 수단 F2다(순서 A6 → B2 → B1 → F2 → A4 → A5 → B3). `gates`의 `selftest` job은 1분을 조금 넘겨 2분으로 청구되는 일이 많다. 기준선에서 162건 가운데 112건이 60초를 조금 넘겼고(중앙값 62초), 1분 안에 끝나면 112분(PR당 2.8분, 2.8%)이 준다(ADR-0008 후보표 F2). 2026-11-25의 성공한 실행 12건은 job 50~83초, 그 가운데 6건이 60초를 넘었다. 준비 단계가 8~12초, 시나리오 실행(`self-test` 단계)이 37~52초다. 실행기(`scripts/selftest/run.ts`의 `runSelfTest`)가 시나리오 10개를 한 프로세스에서 하나씩 차례로 돌린다.

시나리오를 나란히 돌려 시나리오 실행을 줄인다. 시나리오와 판정은 그대로 둔다(설계서 12.4절). 시나리오의 도구(`ctx.cli`, `ctx.hook`, `sample.git`)가 `spawnSync`로 자식 프로세스를 기다리므로 한 프로세스 안의 Promise로는 나란히 돌지 않는다. 시나리오마다 자식 프로세스를 띄운다.

수용 기준:

1. `runSelfTest`가 시나리오마다 자식 프로세스를 띄워 나란히 돌린다. 동시에 도는 수의 기본값은 `os.availableParallelism()`이고 시나리오 수를 넘지 않는다. `runSelfTest`의 `jobs`와 CLI `self-test --jobs <N>`(1 이상의 정수, 아니면 종료 코드 2)으로 바꿀 수 있다. 동시 수가 1이거나 돌릴 시나리오가 하나면 지금처럼 실행기 프로세스 안에서 차례로 돈다.
2. 보고서의 형식(`version: 1`, `headSha`, `results`의 `id`·`covers`·`state`·`detail`)과 결과 순서(파일 이름순)는 그대로다. 시나리오의 시간 제한(기본 120초, `timeoutSec`)은 그 시나리오가 시작한 때부터 잰다.
3. 나란히 돌 때 `pass`가 아닌 시나리오는, 나란히 도는 것이 모두 끝난 뒤 파일 이름순으로 하나씩(다른 시나리오와 겹치지 않게) 한 번 더 돌리고 그 결과를 보고서에 쓴다.
   - 시간 제한으로 끝낸 시도가 하나라도 생기면(나란히 돌 때든 다시 돌릴 때든) 그 뒤로는 다시 돌리지 않는다. 남은 시나리오는 그때까지의 결과(나란히 돌 때의 결과) 그대로다. 그런 실행은 이미 `error`가 있어 판정이 바뀌지 않고, 다시 돌리는 시도가 끝낸 시도의 남은 프로세스와 겹치지 않는다(제작자 결정 2026-11-26, F1).
   - 다시 돌리는 방법은 첫 시도가 끝난 모양으로 정한다. 결과 파일 없이 스스로 끝났으면(자식을 띄우지 못한 경우 포함. 자식 진입점이 깨졌을 수 있다) 실행기 프로세스 안에서 지금 방식으로 돌린다. 시나리오가 `fail`·`error`를 냈으면 자식 프로세스로 돌리고 4의 시간 제한을 둔다.
   - 다시 돌려 통과하면 `detail`에 나란히 돌 때의 결과를 함께 적고, CLI 요약 줄에 다시 돌린 수를 적는다. 다시 돌려도 `pass`가 아니면 다시 돌린 결과(`fail`·`error`)다.
4. 자식 프로세스의 시간 제한: 자식을 띄운 때부터 시나리오의 시간 제한(`timeoutSec`, 기본 120초)에 여유(기본 30초)를 더한 시간 안에 끝나지 않으면, 실행기가 그 자식과 그 아래 프로세스를 모두 끝낸다. 아래 프로세스는 부모 pid로 찾고, 새 세션·프로세스 그룹으로 띄운 것(runner가 띄우는 에이전트 세션)도 포함한다(POSIX는 `ps`로 자손을 찾아 `SIGSTOP`으로 멈추기를 더 늘지 않을 때까지 되풀이한 뒤 모두 `SIGKILL`, Windows는 `taskkill /T /F`). 그 시도는 `error`다. 끝낸 뒤에는 자식 프로세스가 끝난 것(`exit`)만 보고 넘어간다. 스스로 끝난 자식도 `exit` 뒤 1초 안에 `close`가 오지 않으면 넘어간다. 어느 경로로 끝나든 넘어갈 때 자식의 stderr 파이프를 닫아, 남은 프로세스가 그 파이프를 쥐고 있어도 실행기(프로세스)가 기다리거나 끝나지 못하는 일이 없다(F5). 남는 한계: 끝내기 직전에 중간 부모가 끝나 고아가 된 자손(새 세션으로 띄운 것)은 부모 pid로 찾지 못해 남을 수 있다. 그래서 끝낸 시도가 생기면 다시 돌리지 않는다(3, 의사결정 로그). 대기열에서 기다린 시간은 셈하지 않는다. 여유는 `runSelfTest`의 `childGraceSec`로 바꿀 수 있다(테스트가 줄인다. CLI에는 두지 않는다).
5. CLI 요약 줄이 `self-test: 통과 (시나리오 N개, 나란히 M개, 다시 돌린 것 K개, S초)` 꼴로 동시 수와 걸린 시간을 낸다(실패면 `통과` 자리가 지금처럼 `실패 N건`). 병합 뒤 `selftest` job의 로그에서 새 실행기로 돈 실행을 이 줄로 가린다.
6. 테스트(`scripts/test/selftest.test.ts`):
   - 서로를 기다리는 두 시나리오가 나란히 돌아 통과한다(차례로 돌면 실패한다). 동시 수가 `jobs`를 넘지 않는다. 결과가 파일 이름순이다.
   - 나란히 돌 때만 실패하는 시나리오는 자식으로 혼자 다시 돌려 `pass`가 되고 `detail`에 표시가 남는다. 늘 실패하는 시나리오는 `fail`이다.
   - 결과 없이 스스로 끝나는 자식은 `error`가 되고 실행기 안에서 다시 돌린다.
   - 끝나지 않는 시나리오(짧은 `timeoutSec`와 `childGraceSec`)는 시간 제한으로 끝내 `error`가 되고 다시 돌리지 않는다(시작 표시가 한 번). 함께 돌다 `fail`을 낸 시나리오도 다시 돌리지 않는다(`reruns` 0). 그 시나리오가 띄운 자손 프로세스(같은 그룹의 것과, 새 세션으로 띄운 것)가 모두 끝나 있다. 함께 돈 다른 시나리오의 결과는 보고서에 남는다.
   - 다시 돌리는 시도가 시간 제한으로 끝내지면 그 뒤의 시나리오는 다시 돌리지 않는다(나란히 돌 때만 실패하고 혼자 돌면 끝나지 않는 시나리오와 늘 실패하는 시나리오로 본다).
   - 중간 부모가 먼저 끝나 고아가 된 손자(새 세션)가 자식의 stderr 파이프를 쥐고 도는 시나리오도, 실행기가 시간 제한으로 끝낸 뒤 기다리지 않고 `error`로 넘어가 보고서를 돌려준다(그 손자는 테스트가 끝낸다).
   - 결과를 쓰고 스스로 끝난 자식의 손자(새 세션)가 stderr 파이프를 쥐고 있어도, 실행기를 따로 프로세스로 띄우면 그 프로세스가 보고서를 낸 뒤 기한(30초) 안에 끝난다(F5).
   - 대기열에서 기다린 시나리오도 시작한 때부터 시간 제한을 온전히 받는다. 여유를 1초로 줄이고, 앞 시나리오를 기다린 시간을 더하면 `timeoutSec + childGraceSec`를 넘는 꼴로 만들어, 다시 돌리지 않고(`reruns` 0, `detail`이 제목 그대로) 통과하는지 본다. 대기열 시간을 셈하는 구현이면 첫 시도가 끝내지거나 시간 제한에 걸려 다시 돌리게 되어 실패한다.
   - CLI `--jobs`의 잘못된 값은 종료 코드 2다.
   - 기존 테스트(이 리포의 하네스가 모든 시나리오를 통과, 약화된 사본에서 해당 시나리오 실패, 자격증명을 넘기지 않음)가 고치지 않고 통과한다.
7. 로컬에서 이 리포의 하네스로 `self-test --jobs 1`과 `--jobs 2`를 바로 잇달아 돌려(각각 앞에 `uptime`) 두 요약 줄의 시간과 부하를 진행 로그에 `시간 재기:` 줄로 남긴다. AC가 두 모드를 다시 돌려 통과하는지와 그 줄이 있는지를 본다. PR의 CI `check`(arm64 2코어. `selftest.test.ts`가 기본 동시 수로 모든 시나리오를 돌린다)가 통과한다.
8. 문서: 설계서 12.4절(실행 방법, `--jobs`, 나란히 돌리기와 다시 돌리기), `docs/harness/architecture.md`의 `scripts/selftest/` 설명, 변경 조각.
9. 병합 뒤 새 실행기로 돈 `selftest` job(로그의 요약 줄에 `나란히`가 있는 것)의 걸린 시간을 Issue #247에 남긴다. 병합 뒤 처음 10개(병합 뒤 7일 안에 10개가 안 되면 그때까지 돈 것)를 본다. 60초를 넘는 job이 있으면 워크플로의 준비 단계를 줄이는 후속 Issue를 연다.
10. 제작자 head 승인 요청(`pr-ready`)은 2026-11-29 00:00 UTC 뒤에 한다(B1의 넣기 전 값 2026-11-25~28과 섞이지 않게).
