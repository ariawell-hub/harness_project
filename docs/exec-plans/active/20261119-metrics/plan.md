# 17.2절 지표 집계: metrics 명령으로 QUALITY_SCORE.md를 채운다

## 목표와 수용 기준

설계서 17.2절은 지표를 "주간 정기 작업에서 집계해 `docs/QUALITY_SCORE.md`에 기록한다"고 정한다. 지금은 집계 수단이 없어 `docs/QUALITY_SCORE.md`의 값이 모두 `—`다. 로드맵 3단계(파일럿)의 완료 기준이 "17.2절 파일럿 판정 지표가 수집된다"이므로, 파일럿 착수 전에 지표를 집계하는 명령을 만들고 지금까지의 자료로 첫 집계를 기록한다. 주 1회 자동 실행은 4단계(TD-11)에 남기고, 이 계획은 그 정기 작업이 부를 명령까지 만든다.

수용 기준:

1. `node scripts/harness.ts metrics --since <YYYY-MM-DD> --until <YYYY-MM-DD>`가 그 기간(UTC 날짜, 양끝 포함)에 병합된 PR을 대상으로 지표를 집계해 마크다운으로 표준 출력에 낸다. 날짜를 주지 않으면 `until`은 오늘(UTC), `since`는 `until`의 6일 전이다. 읽기만 한다(GitHub에 쓰지 않는다).
2. 파일럿 판정 지표 넷(병합 후 결함, 검증 누락, 오탐, PR당 대기 시간·사용량)이 step0의 정의대로 계산된다. 고정한 입력으로 계산 함수를 부르는 테스트가 값을 단언한다.
3. 명령은 파일을 쓰지 않는다. 출력은 `docs/QUALITY_SCORE.md`의 표식 구간(`<!-- metrics:begin -->` ~ `<!-- metrics:end -->`)에 그대로 붙여 넣는 글이고 prettier를 통과한다. 같은 자료로 두 번 실행하면 출력이 같다. 문서에는 작업자가 worktree 안에서 출력을 붙여 넣어 기록한다.
4. 자료를 끝까지 읽지 못하면(GitHub 조회 실패, 결과가 조회 상한에 닿음) 종료 코드 2로 끝나고 표준 출력에 집계 결과를 내지 않는다.
5. 상시 지표는 지금 자료로 잴 수 있는 것을 모두 잰다(step1: GitHub 자료, step2: 리포 파일과 로컬 로그). 잴 수 없는 지표는 값 대신 이유와 TD 번호를 출력한다. step2가 끝나면 17.2절의 상시 지표 항목마다 값 또는 이유 한 줄이 집계 결과에 있다.
6. 집계 결과에는 수와 PR·Issue 번호만 적는다. PR·Issue·지적의 제목과 본문 같은 외부 입력 문자열은 문서에 옮기지 않는다(14.6절).
7. `docs/QUALITY_SCORE.md`에 지표별 측정 정의가 있고, 이 리포의 2026-11-11부터 step0 작업일까지의 첫 집계가 기록된다. 설계서 17.2절, `docs/harness/architecture.md`, `CHANGELOG`, 기술 부채 표(TD-11)가 바뀐 상태와 맞는다.

- 결정: 문서를 읽고 쓰는 동안 프로세스의 작업 폴더를 문서 폴더로 옮기고 상대 이름으로만 다룬다(F14). / 이유: Node에는 폴더 fd 기준으로 여는 API(`openat`)가 없다. 작업 폴더는 경로가 아니라 폴더 자체에 묶이므로, 들어온 폴더의 실제 경로를 확인한 뒤에는 `docs` 경로가 바뀌어도 밖을 쓰지 않는다. 끝나면 원래 폴더로 돌아간다(동기 코드라 그 사이 다른 코드가 돌지 않는다). / 버린 대안: 쓰기 직전에 경로를 한 번 더 확인하기(확인과 열기 사이의 틈이 남는다), 자식 프로세스를 문서 폴더에서 띄워 쓰게 하기(같은 효과에 프로세스가 하나 더 든다).
- 결정: `MetricsOptions.writeBytes`(파일에 바이트를 쓰는 함수, 기본 `writeSync`)를 더한다(F17). / 이유: 짧은 쓰기와 도중 실패를 테스트에서 만들 방법이 필요하다. 명령행에서는 넘기지 않는다.

R3은 이 명령이 worktree 밖을 쓰지 않게 하는 규칙이고, 이 명령은 확인할 수 있는 지점마다 확인한다. / 버린 대안: 다른 사용자가 쓸 수 있는 폴더(그룹 쓰기 권한 포함)에서는 `--write`를 거부하기(umask 002인 환경에서 쓰지 못하게 되고, 같은 사용자의 프로세스는 여전히 막지 못한다). 반박이 두 번 받아들여지지 않으면 제작자에게 묻는다(절차서 8절 교착).
- 방법 전환(F14·F18, 3회): 가설 "쓰는 동안의 바꿔치기는 확인을 더 촘촘히 하면 막힌다" / 시도한 방법 문서 경로의 링크 확인(1라운드), 문서 폴더에 작업 고정(2라운드), 이름 바꾸기 직전·직후 재확인과 반박(3라운드) / 폐기 이유 확인과 이름 바꾸기 사이의 틈은 경로 기반 API로 닫을 수 없고, 반박은 "다른 사용자도 그 틈을 쓸 수 있다"는 점에 답하지 못했다 / 새 방법 틈을 쓸 수 있는 주체를 줄인다: worktree 루트와 `docs` 폴더의 소유자가 이 사용자이고 그룹·기타 쓰기 권한이 없을 때만 쓴다. 3라운드에 버린 대안이었는데(umask 002 환경에서 `chmod go-w`가 필요해진다), 검증자가 제안한 방향이고 기본 환경(umask 022, CI)에는 영향이 없어 받아들인다. 남는 것은 같은 사용자의 프로세스와 root다. 이들은 문서를 직접 쓸 수 있어 이 명령이 막을 대상이 아니다. 이 점은 2회째 반박으로 답하고, 받아들여지지 않으면 제작자에게 묻는다(절차서 8절 교착).
- 결정(제작자, 교착 F14·F18): 선택지 A "지적대로 두 가지를 더 막는다"(Windows에서 `--write` 거부, worktree 루트의 상위 폴더 권한 확인). / 이유: codex가 5라운드에 남은 이유를 이 둘로 짚었다. / 버린 대안: B `--write`를 이 step에서 뺀다(계획 재검증이 필요하고 주 1회 기록의 쓰기 수단을 따로 만들어야 한다), C 지금 구현으로 둔다(제작자가 P0을 닫는 수단이 절차에 없다), D PR을 닫는다. 이번에도 열리면 더 고치지 않고 다시 묻는다(F14는 다섯 번째 시도다).
- 결정: worktree 위의 폴더에는 root 소유와 sticky를 허용한다. / 이유: `/`, `/Users`, `/home`은 root 소유이고 `/tmp`는 누구나 쓰는 sticky 폴더다. 이들을 거부하면 어디서도 쓸 수 없다. root는 무엇이든 쓸 수 있어 막을 대상이 아니고, sticky 폴더에서는 항목의 소유자만 그 항목을 옮기거나 지운다. `docs`와 worktree 루트에는 허용하지 않는다(이 사용자의 것이어야 한다).

- 결정(제작자, F14·F18 5회 실패): 선택지 B "`--write`를 뺀다". 명령은 출력만 하고, 문서에는 작업자가 출력을 표식 구간에 붙여 넣어 기록한다. / 이유: 쓰는 순간에 다른 프로세스가 폴더나 임시 파일을 바꿔치기하는 경우를 여섯 라운드에 걸쳐 막았지만(링크 확인, 폴더 고정, 직전·직후 재확인, 권한 확인, Windows 거부, 상위 폴더 확인) 라운드마다 더 드문 경우가 남았다(마지막은 macOS ACL). - 결정: `replaceBlock`을 없애고 표식 줄(`BEGIN`, `END`)은 남긴다. / 이유: 명령이 문서를 고치지 않으므로 구간을 바꾸는 함수를 부를 곳이 없다. 표식은 붙여 넣을 자리를 알려 주고, 테스트가 이 리포 문서의 구간 구조를 볼 때 쓴다.
