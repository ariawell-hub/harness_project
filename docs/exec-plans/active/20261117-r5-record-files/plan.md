# feat: R5 '먼저 실패한 테스트' 기록을 명령으로 남기고 완료 처리에서 확인한다

## 목표와 수용 기준

R5(TDD)의 "먼저 실패한 테스트" 기록이 문장으로 대체되지 않게 한다. #102 step5(PR #110)에서 대화 세션이 테스트를 구현보다 먼저 쓰고도 구현 전에 실패하는 실행을 돌리지 않았고, 테스트 4개가 첫 실행에 통과했다. 지금 이 기록은 절차서의 문장, PR 템플릿의 자유 서술 칸, 검증자의 판단에만 기댄다. 제작자 결정(2026-11-17 대화)에 따라 기록을 명령의 실행 결과로 남기고 `complete-step`이 그 기록을 확인하게 한다.

이 일은 계획 `20261117-r5-fail-first`로 시작했다. 그 계획의 step0(PR #112, 병합됨)이 만든 `fail-first "<테스트 명령>"`은 인자를 셸로 실행해 L1 훅의 우회로가 됐다: 금지 명령을 이 명령 안에 감싸면 훅이 R20·R2·R14·R4를 판정하지 못한다(진행 로그). 제작자 결정(2026-11-17 대화)에 따라 먼저 되돌리고(step0), 임의 명령을 실행하지 않는 방식으로 다시 만든다(step1). 옛 계획은 다음 step(완료 처리 검사)의 지시서가 되돌려질 명령에 기대고 있고 실행 중인 step의 지시서는 그 PR에서 고칠 수 없어(`plan-gate`), 폐기하고 이 계획으로 이어 간다.

수용 기준:

1. **되돌리기**: 옛 계획의 step0이 main에 넣은 `fail-first` 명령(코드, 테스트, CLI 연결, 문서 줄)이 main에서 빠진다. 하네스 CLI에 인자로 받은 문자열을 셸로 실행하는 명령이 남지 않는다. 옛 계획 `20261117-r5-fail-first`는 `abandoned`로 `completed/`에 옮겨진다.
2. **기록 명령(다시 만든다)**: `node scripts/harness.ts fail-first <테스트 파일>`이 계획 브랜치의 worktree에서 그 파일 하나를 실행한다(한 번에 하나: 파일마다 따로 실행해야 그 파일이 실패했는지 알 수 있다). 셸을 거치지 않고, 설정의 "테스트 하나를 실행하는 명령"(`ci.repro.command`) 뒤에 파일 경로를 붙여 프로세스로 띄운다(시간 제한 `limits.acTimeoutSec`). 인자는 worktree 안에 있는 테스트 파일의 상대 경로만 받는다(심볼릭 링크는 실제 대상이 worktree 안이어야 한다). 그 밖의 인자(셸 명령 문자열, `-`로 시작하는 값, 절대 경로, `..`, 없는 파일, 테스트 파일이 아닌 경로, worktree 밖을 가리키는 심볼릭 링크)는 아무것도 실행하지 않고 종료 코드 2다.
3. **기록 조건**: 종료 코드가 0이 아니고 출력에 단언 실패 정규식(`ci.repro.failPattern`)이 보일 때만 기록을 남기고 종료 코드 0으로 끝난다. 통과한 실행(종료 코드 0), 시간 초과, 단언 실패가 아닌 실패(모듈을 찾지 못함, 문법 오류)는 기록하지 않고 종료 코드 1과 이유를 낸다. 계획 브랜치가 아니거나 `ci.repro`가 없는 리포에서는 종료 코드 2다.
4. **기록 위치와 내용**: 기록은 git이 추적하지 않는 worktree별 하네스 상태 폴더의 `fail-first.jsonl`에 한 줄씩 쌓인다(시각, 계획 id, step, 실행한 테스트 파일, 종료 코드, HEAD). 테스트 출력의 내용은 기록·계획·명령의 stdout 어디에도 저장하거나 옮기지 않는다: 단언 메시지에 시크릿이 섞일 수 있다. 출력은 단언 실패인지 판정하는 데만 쓴다. 계획 파일이나 PR 본문에 손으로 쓴 문장은 기록이 아니다.
5. **예외 기록**: `node scripts/harness.ts fail-first --exempt "<사유>"`가 실행 없이 예외를 같은 파일에 남긴다(R5의 예외: 문서·설정·순수 리팩터, 기록을 남기지 못한 경위). 사유가 비면 종료 코드 2다.
6. **완료 처리 검사**: `complete-step`은 그 step의 변경(merge-base 대비, 작업 트리 포함)에 테스트 파일이 있으면 그 계획·step의 기록이나 예외를 요구한다. 기록은 그 파일이 이 step이 바꾼 테스트 파일일 때만 인정한다(다른 테스트 파일의 실패는 기록이 아니다). 없으면 계획 파일을 바꾸지 않고 종료 코드가 0이 아니며 고치는 법을 출력한다. 있으면 진행 로그에 `먼저 실패한 기록(R5)` 또는 `R5 예외` 한 줄(파일, 종료 코드, 기록 시각, HEAD 또는 사유)을 더해 계획 전용 커밋에 담는다. 테스트 파일이 바뀌지 않은 step의 동작은 그대로다.
7. **runner**: step 세션 프롬프트가 `fail-first` 사용을 지시한다. 테스트 파일을 바꾸고 기록 없이 끝난 세션은 runner의 완료 처리 실패(`plan:complete`)로 세어지고 다음 세션 프롬프트에 그 이유가 들어간다.
8. **자체 테스트**: 시나리오 `r5-fail-first`가 샘플 리포에서 위 2·3·6을 CLI로 확인한다(기록 없이는 완료 처리가 막힌다, 통과하는 테스트는 기록되지 않는다, 셸 명령 문자열은 실행되지 않는다, 기록 뒤에는 완료된다). 완료 처리 검사를 뺀 사본에서 이 시나리오가 실패한다.
9. **문서**: 설계서 5.1절 R5 행과 12.4절 시나리오 표, 절차서 3·4절(인정되는 기록의 형식), PR 템플릿의 R5 줄, `AGENTS.md` 작업 루프 3번, 코드 구조 문서, `CHANGELOG`, TD-4(남는 범위)를 고친다.

  - 테스트 파일 안의 코드가 하는 일의 통제. 세션이 쓴 테스트 파일을 `node --test`로 실행하는 것은 지금도 무인 권한 프로필이 허용한다. L0 샌드박스(4단계)의 몫이다.
  - 지적 대응 세션(`review`)과 충돌 해결 세션의 프롬프트. step 세션 프롬프트만 고친다.
  - 기록의 위조 방지. 상태 폴더의 파일을 손으로 만들면 통과한다. 막으려는 것은 부주의한 누락과 문장 대체다.

## 발견 사항

- 인자로 받은 문자열을 셸로 실행하는 하네스 명령은 L1 훅의 우회로가 된다. 훅은 `bash -c`·`eval`의 안쪽은 다시 판정하지만(`scripts/hooks/shell.ts`) 하네스 자신의 명령 인자는 들여다보지 않는다. 검증자 둘 다 놓쳤다. 다시 만드는 명령은 셸을 쓰지 않고, step1의 테스트가 "셸 명령 문자열은 실행되지 않는다"를 확인한다. 같은 꼴의 명령을 새로 만들지 않게 설계서 13.1절에 한 줄을 적는다(step2 문서). → 처리: #111
- `ci.repro`가 없는 프로파일(core, web)로 만든 리포에서는 다시 만드는 `fail-first`가 실행할 명령을 모른다(종료 코드 2). 예외 기록만 쓸 수 있다. 프로파일에 `ci.repro`를 넣는 일은 판정 관련 설정 변경이라 이 계획에서 하지 않는다. step2에서 TD로 등록한다. → 처리: #111
- `node --test` 안에서 도는 테스트가 `node --test`를 자식으로 띄우면 `NODE_TEST_CONTEXT`가 넘어가 자식이 테스트 파일을 실행하지 않고 종료 코드 0으로 끝난다("run() is being called recursively" 경고). 통과로 보이는 거짓 결과라 테스트에서 이 변수를 빼야 한다. 에이전트의 셸과 자체 테스트 실행기(환경 변수 허용 목록)에는 이 변수가 없다. → 처리: [코드 구조 문서](../../../harness/architecture.md)
- 실행할 차례인 step의 지시서를 고쳐야 하는 계획 수정은 그 계획 안에서 할 수 없다(`plan-gate`: 실행 PR은 자기 step 파일을 못 바꾼다, `new-task`: 앞 step이 병합돼야 다음 step). 계획을 폐기하고 새 계획을 만들어야 해서 계획 검증을 처음부터 다시 받는다. 절차서 2절에는 "계획을 고쳐야 하면 진행 로그에 이유를 적고 제작자에게 알린다"만 있고 이 경우의 방법이 없다. step2에서 절차서에 한 줄을 더한다. → 처리: #111
- 고친 P1 지적이 다음 라운드의 승인 판정에서 `fixed`로 닫히지 않고 `open`으로 남는다(PR #112 F1, PR #113 F2: 승인 2건인데 `review-ledger`는 실패). PR #112에서는 반박 형식 댓글을 달고 한 라운드를 더 돈 뒤에야 닫혔다. 계획 검증 단계(계획만 담은 커밋)에서만 그런지, 코드 판정에서도 그런지는 확인하지 않았다. step2에서 TD로 등록한다. → 처리: #111
- PR #110에서 `review/claude`는 "먼저 실패한 기록이 없다"를 확인하고도 사후 변이 확인을 받아들여 승인했다. 설계서 5.1절은 절차 항목 누락을 P1 지적으로 정한다. 검증 기준을 고치는 일은 제작자가 고르지 않았으므로 이 계획에서 바꾸지 않는다. → 처리: #111
