# 비공개 리포에서의 Actions 비용 설계: 공개 기간에 재고, 예산과 절감 수단을 정한다

## 목표와 수용 기준

2026-11-18과 11-20에 Actions의 포함 사용량과 지출 한도가 바닥나 모든 job이 시작되지 않았다(Issue #126, #170). 2026-11-17~20의 실측으로는 월 $180~320의 속도다. 제작자는 2026-11-21에 이 리포를 공개로 바꿨고(표준 러너 무료), 하네스를 실제로 쓸 프로젝트는 비공개여야 한다고 정했다. 그래서 비공개 리포에서 감당할 수 있는 Actions 비용이 하네스의 요구사항이 된다.

공개 리포는 청구가 0이라 청구서로는 비용을 볼 수 없다. 이 계획은 (1) Actions 실행 기록에서 "비공개였다면 청구됐을 값"을 재는 명령을 만들고, (2) 그 값으로 판단하는 절차와 기준선을 문서로 남기고, (3) 절감 수단을 조사해 제작자가 고를 수 있는 결정 기록(ADR)으로 만든다. 고른 수단의 구현은 이 계획에 넣지 않는다.

수용 기준:

1. `node scripts/harness.ts actions-cost --since <YYYY-MM-DD> --until <YYYY-MM-DD>`가 그 기간(UTC 날짜, 양끝 포함)에 만들어진 Actions 실행의 job을 읽어, job마다 올림한 분과 러너 단가로 "비공개였다면 청구됐을 값"을 계산해 마크다운으로 표준 출력에 낸다. 읽기만 한다(GitHub에 쓰지 않고 파일을 쓰지 않는다).
2. 계산 규칙이 step0의 정의대로이고, 고정한 입력으로 계산 함수를 부르는 테스트가 값을 단언한다: 돌지 않은 job은 0분, 돈 job은 초를 분으로 올림(최소 1분), 다시 실행한 시도는 job 기록의 시도 번호로 갈라 따로 청구(일부 job만 다시 실행한 경우 포함), 단가를 모르는 러너와 self-hosted 러너는 금액에 넣지 않고 따로 보인다.
3. 출력에 합계, 워크플로별, job별, 날짜별, PR별, PR head 하나당 평균(push 한 번의 추정값. 분자와 분모가 같은 실행 집합이다), 올림으로 붙은 몫, 30일 환산값이 있다. PR 밖 실행(main 등)과 PR을 찾지 못한 실행은 숨기지 않고 각각 따로 합산한다.
4. 자료를 끝까지 읽지 못하면 종료 코드 2로 끝나고 표준 출력에 결과를 내지 않는다. 받은 수가 맞아도 실행이나 job이 중복으로 온 응답(읽는 동안 목록이 바뀌어 빠진 것이 있을 수 있다)은 끝까지 읽지 못한 것이다. 기간이 틀리면 GitHub을 읽기 전에 종료 코드 1로 끝난다.
5. 출력에는 수, PR 번호, 날짜, 그리고 명령을 실행한 체크아웃의 워크플로 파일에 있는 워크플로·job 이름만 적는다. 실행 기록에만 있는 이름(외부 PR이 정할 수 있다)은 글자가 무난해도 적지 않고 `(기타)`로 합친다. PR 제목·브랜치 이름 같은 외부 입력 문자열과 계정 이름은 옮기지 않는다(설계서 14.6절).
6. `docs/harness/actions-cost.md`에 판단 절차(예산과 그 상태, 다시 재는 시점, 판단 시점, 재는 방법)와 기준선(2026-11-17~20, 비공개 기간. 잰 날짜와 명령)이 있고 `docs/index.md`가 가리킨다. 문서에 붙인 기준선은 명령의 출력과 같다(step1의 AC가 다시 재서 비교한다).
7. 절감 수단마다 예상 절감, 잃는 보장, 바꿔야 하는 것, 되돌리는 방법, 사실관계의 확인 상태를 적은 ADR이 있고(후보 14개 이상, 묶음 둘 이상과 묶음별 비용 추정), 상태(제안 또는 채택)와 제작자가 고른 수단·순서(고르기 전이면 추천)가 적혀 있다. 설계서, ADR 색인, 기술 부채 표가 ADR 파일을 가리킨다.
8. `node scripts/harness.ts check` 통과.

## 의사결정 로그

- 결정: `metrics`에 잇지 않고 `actions-cost` 명령을 따로 둔다. / 이유: `metrics`의 출력은 `docs/QUALITY_SCORE.md`에 붙이는 주간 지표이고 PR 단위로 읽는다. 비용은 실행마다 job 목록을 읽어야 해 조회 수가 실행 수만큼 든다(1,000건이면 1,000회). 주간 집계가 그만큼 느려지면 안 된다. / 버린 대안: `metrics`에 절을 더하기(느려지고, 출력 문서가 다르다).
- 결정: 위험도는 normal이다(`new-task`에는 low로 넣었다가 고쳤다). / 이유: step0이 일반 코드다. 읽기만 하는 명령과 문서이고 검사·권한·워크플로를 바꾸지 않는다. 보안 설계를 바꾸는 절감 수단은 이 계획의 비범위이고 별도 Issue에서 높음으로 한다.
- 결정: 단가는 코드의 표로 두고 확인한 것만 넣는다(2코어 Linux x64 분당 $0.006). / 이유: 지금 워크플로는 모두 `ubuntu-latest`다. 확인하지 않은 단가로 금액을 내면 판단이 틀린다. 모르는 러너는 분만 보인다. / 버린 대안: 설정 파일(`harness.config.json`)에 단가를 두기(설정 스키마가 늘고, 단가는 프로젝트가 아니라 GitHub이 정한다).
- 결정: push 한 번당 비용은 "PR head 하나당 평균"으로 재고 추정값이라고 적는다. / 이유: Actions 실행 기록으로는 push를 직접 셀 수 없다(같은 head에 여러 이벤트가 붙고, 기록만 고친 본문 수정도 게이트를 돌린다). 분자와 분모를 head가 있는 실행으로 맞추면 main 작업량이 섞이지 않아 절감 전후를 비교할 수 있다. / 버린 대안: 리포 전체 청구 분 ÷ PR head 수(처음 계획. main 작업량과 PR 다시 열기에 값이 흔들린다).
- 결정: 출력에 적는 워크플로·job 이름은 체크아웃의 워크플로 파일에서 만든 허용 목록에 있는 것만이다. / 이유: 공개 리포에서는 포크의 PR이 job 이름을 정한다. 글자·길이 조건은 짧은 지시문이나 계정 이름을 막지 못하고, 출력은 `docs/`에 붙는다(14.6절). / 버린 대안: 글자·길이 조건만(처음 계획), 이름을 아예 내지 않기(어느 job이 비싼지 볼 수 없다).
- 결정: step1의 AC가 GitHub을 읽어 기준선을 다시 잰다. / 이유: 문서에 붙인 값이 명령의 출력인지 확인할 다른 방법이 없다. `check`와 테스트는 네트워크를 쓰지 않는다(AC만 쓴다). 지난 기간의 실행 기록은 다시 실행하지 않는 한 바뀌지 않는다. / 버린 대안: 제목만 확인(처음 계획. 빈 문서도 통과한다).
- 결정(제작자, 2026-11-21 대화): 예산은 계정의 포함 사용량(Pro 월 $18) 안이다. 프로젝트 하나가 월 PR 100개를 처리한다고 보고 PR 하나당 $0.18(2코어 Linux 30분 상당)을 목표로 둔다. Pro만으로 해결되는 것이 가장 좋다. / 이유: 하네스를 쓸 프로젝트는 비공개여야 하고, 추가 지출 없이 돌아야 한다. / 영향: step2의 묶음은 이 예산에 드는 조합을 먼저 찾고, 들지 않으면 가장 가까운 조합과 모자라는 폭을 적는다.

## 발견 사항

- 판정 워크플로(`judge-claude`, `judge-codex`)와 `revert`는 `workflow_run`으로 시작해 실행 기록의 브랜치가 main이고 PR 목록이 비어 있다. PR을 찾으려면 다른 자료가 필요하다. PR head 커밋의 커밋 상태(`review/claude` 등)의 `target_url`이 그 실행을 가리킨다(2026-11-21에 PR #169에서 확인). → 처리: 해당 없음(step0의 작업에 반영했다)
- job 목록 조회는 기본으로 마지막 시도만 준다. 다시 실행한 실행의 앞선 시도는 `filter=all`로 받아야 한다(같은 날 PR #169의 판정 실행에서 확인: 시도 1의 job은 시작하지 못했고 시도 2가 돌았다). → 처리: 해당 없음(step0의 작업에 반영했다)
- 리포가 공개되면 포크의 PR이 `pull_request` 워크플로의 job 이름을 정할 수 있다. job 이름도 외부 입력이다. → 처리: 해당 없음(step0의 출력 규칙에 반영했다)
