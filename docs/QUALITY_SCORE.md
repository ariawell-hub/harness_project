# 품질 점수

설계서 17.2절의 지표를 `node scripts/harness.ts metrics`로 집계해 적는다. 주 1회 실행은 정기 작업(4단계, TD-11)이 맡는다. 그 전에는 작업 worktree에서 직접 실행한다.

```bash
node scripts/harness.ts metrics                      # 최근 7일(UTC)
node scripts/harness.ts metrics --since 2026-11-11   # 그날부터 오늘(UTC)까지
node scripts/harness.ts self-test --out <임시 파일>   # 자체 테스트 통과율까지 내려면 먼저 보고서를 만든다
node scripts/harness.ts metrics --self-test-report <임시 파일>
```

- 기간은 UTC 날짜(`YYYY-MM-DD`)이고 양끝을 포함한다. `--until`이 없으면 오늘(UTC), `--since`가 없으면 `--until`의 6일 전이다.
- GitHub을 읽기만 한다. 하나라도 다 읽지 못하면 값을 내지 않고 종료 코드 2로 끝난다. 병합된 PR마다 조회를 네 번씩 하므로(커밋, 커밋 상태, 같은 브랜치의 PR, 원장) PR이 100개면 몇 분 걸린다.
- 리포 파일(계획, 문서)과 runner 로그는 명령을 실행한 체크아웃과 머신의 것을 읽는다. runner 로그가 없는 머신에서는 runner 지표가 "이 머신에 runner 로그 없음"으로 나온다.
- `--self-test-report`는 `self-test --out <파일>`이 쓴 보고서다. 명령은 `self-test`를 실행하지 않는다(몇 분 걸리고 샘플 리포를 만든다). 파일이 없거나 형식이 다르면 GitHub을 읽기 전에 종료 코드 1로 끝난다.
- 명령은 파일을 쓰지 않는다. 출력을 아래 "집계 결과"의 두 표식 줄(`metrics:begin`, `metrics:end` 주석) 사이에 그대로 붙여 넣어 기록한다. 작업 worktree에서 하고, 표식 줄과 내용 사이에는 빈 줄을 하나 둔다.
- 지난 집계는 이 파일의 git 이력에 남는다.

### 파일럿 판정 지표

- **병합 후 결함**: 세 값을 따로 낸다. 같은 결함이 둘 이상에 잡힐 수 있어 더하지 않는다.
  - main `check` 실패: 기본 브랜치의 push로 돈 `check` 워크플로 실행 가운데 기간 안에 만들어지고 실패로 끝난 것의 수. 실행 목록은 실행마다 마지막 시도의 결과만 준다. 그래서 다시 실행해 통과한 실행은 여기에 들지 않고 "재실행 뒤 통과한 실행"으로 따로 적는다.
  - revert PR: 기간 안에 병합된 PR 가운데 head 브랜치가 `revert/`로 시작하는 것.
  - 버그 Issue: 기간 안에 만들어진 `bug` 라벨 Issue(닫힌 것 포함).
- **검증 누락**: 검증을 통과해 병합된 PR 가운데, 그 병합 커밋에서 main `check`가 성공에서 실패로 바뀐 PR.
  - main `check` 실행(성공·실패로 끝난 것)을 만들어진 순서로 놓고(같은 초에 만들어진 실행은 실행 번호 순), 실패이면서 직전 실행이 성공인 것만 "실패로 바뀐 실행"으로 본다. 이미 실패 중인 main에 이어진 실패는 앞선 결함과 같은 것으로 보고 세지 않는다.
  - 기간의 첫 실행은 기간 직전의 마지막 실행과 견준다(최대 7일을 거슬러 찾는다). 찾지 못하면 "전환 여부 미확인"으로 따로 적고 검증 누락에 넣지 않는다.
  - 실패로 바뀐 실행의 커밋이 기간 안에 병합된 PR의 병합 커밋이 아니면 "원인 PR을 찾지 못한 실행"으로 따로 적는다.
  - 버그 Issue는 원인 PR과 잇는 근거가 없어 넣지 않는다. 검증자가 놓친 것인지는 사람이 가른다.
- **오탐**: 기간 안에 병합된 PR의 지적 원장에서 센다. 차단 지적은 등급이 P0·P1이고 미룸(`deferred`)이 아닌 지적이다. 그 가운데 재현 테스트가 "재현 안 됨"으로 끝난 것과 반박이 받아들여진 것(`rejected`)의 합집합이 오탐이다. 비율은 오탐 수 ÷ 차단 지적 수다.
  - 계획 검증(G1)의 지적도 같은 원장에 있어 함께 센다.
- **PR당 대기 시간**: PR을 만든 때부터 병합까지의 시간. 중앙값과 최댓값(분). 초안으로 둔 시간과 제작자 승인을 기다린 시간이 들어 있다.
- **PR당 사용량**
  - Actions 실행 시간: 기간 안에 만들어지고 끝난 모든 워크플로 실행의 시작부터 끝까지의 합(분). 청구 분(job마다 분 단위로 올림)과 다르고, 대기 시간이 든 값이다. 병합되지 않은 PR의 실행도 들어 있다.
  - 판정 워크플로: 그중 `judge-claude`·`judge-codex` 실행의 합.
  - 판정 수: 병합된 PR의 원장에 기록된 판정(라운드) 수의 합.
  - 실패로 끝난 판정 워크플로 실행: 검증자 장애·사용 한도·판정 형식 오류로 판정 없이 끝난 실행이 여기에 든다.
  - 검증자 구독의 사용량(토큰)은 GitHub에 남지 않아 재지 않는다.
- **세지 못한 항목**: 시각이 깨져 계산에서 뺀 PR·실행의 수. 0이 아니면 값을 그대로 믿지 않는다.

### 상시 지표

GitHub 자료, 리포 파일(계획, 문서), 로컬 로그(runner 로그, 자체 테스트 보고서)로 잰다. 지금 자료로 잴 수 없는 지표는 값 대신 이유와 기술 부채 번호를 적는다. 설계서 17.2절의 상시 지표 항목마다 값 또는 이유 한 줄이 집계 결과에 있다.

- **PR 리드타임(계획 생성 → 병합)**: 계획 frontmatter의 `claimed_at`(`new-task`가 적는다)부터 PR 병합까지의 시간. 중앙값과 최댓값(분).
  - 계획은 PR의 head 브랜치 이름(`<type>/<계획 id>` 또는 `<type>/<계획 id>-s<N>`)으로 명령을 실행한 체크아웃의 `docs/exec-plans/`에서 찾는다. 둘째 step부터의 PR도 계획 생성 시각부터 잰다.
  - 계획을 찾지 못한 PR(revert PR처럼 브랜치 이름이 계획 형식이 아닌 것, 계획 파일이 없는 것)은 빼고 그 수를 따로 적는다.
- **CI 첫 통과율**: 첫 `check` 실행이 첫 시도에 통과한 PR 수 ÷ 실행을 찾은 PR 수.
  - Actions 실행 목록은 병합된 PR의 번호를 주지 않는다. 그래서 실행을 head 브랜치 이름, 커밋 SHA(PR에 든 커밋), 시각(PR을 만든 때부터 병합까지), 이 리포의 브랜치에서 돈 실행인지로 PR에 잇는다.
  - 같은 head 브랜치 이름으로 열린 PR이 둘 이상이면 어느 PR의 실행인지 가를 수 없어 뺀다. 포크에서 온 PR도 뺀다. 이들은 "실행을 이을 수 없는 PR"로 따로 적는다. 이을 수 있지만 실행을 찾지 못한 PR도 분모에서 빼고 따로 적는다.
  - 커밋이 교체된 PR도 "실행을 이을 수 없는 PR"로 뺀다: PR이 열려 있던 동안 같은 브랜치에서 돈 `check` 실행 가운데 SHA가 PR의 커밋 목록에 없는 것이 하나라도 있는 PR이다. 커밋 목록은 병합 때의 것이라, 브랜치 이력이 다시 쓰여 목록에서 빠진 커밋의 실행을 버리고 고르면 실패한 첫 실행이 빠질 수 있다.
  - 실행 목록은 실행마다 마지막 시도의 결과만 준다. 그래서 다시 실행된 첫 실행은 결과와 무관하게 첫 통과로 세지 않는다. 취소로 끝난 첫 실행(바로 뒤의 push로 대체된 것 포함)도 통과가 아니다.
  - PR의 커밋 목록은 PR마다 따로 읽는다. 한 PR의 커밋이 250개 이상이면 목록을 끝까지 읽을 수 없어 그 PR이 든 기간은 집계하지 않는다(종료 코드 2).
- **PR당 리뷰 라운드 수**: PR의 원장에서 검증자별 판정 수 가운데 큰 값. 중앙값, 최댓값, 3라운드를 넘은 PR의 번호(설계서 19절 4단계 완료 기준이 3라운드다). 원장이 없는 PR은 0이다. 계획 검증(G1)의 판정도 같은 원장에 있어 함께 센다.
- **에스컬레이션 수와 사유**: 두 값을 따로 낸다. 라벨과 댓글은 따로 기록돼 같은 사건을 가리킬 수 있고, 날짜 경계에서 서로 다른 기간에 들 수 있다. 더하거나 빼지 않는다.
  - `needs-human` 라벨이 붙은 횟수: 기간 안의 라벨 이벤트 수. 같은 Issue에 다시 붙으면 다시 센다.
  - 사유별 알림 댓글: 봇 계정이 기간 안에 쓴 댓글을 문구로 가른다(5회 실패 중단, 총량 상한 중단, 교착, 갱신 충돌, 그 밖의 중단, 질문, 승인 요청, CI 대기, 자동 revert 불가). 다른 계정이 쓴 댓글은 세지 않는다. 대화 세션이 댓글 없이 라벨만 붙인 사건은 댓글 수에 없다.
- **5회 중단·총량 상한 도달 횟수**: 위 알림 댓글 가운데 5회 실패 중단과 총량 상한 중단의 수. 갱신 충돌과 그 밖의 중단은 넣지 않는다.
- **위험도별 PR 수**: PR head 커밋의 `risk-gate` 커밋 상태 가운데 검증 App이 쓴 가장 최근 기록의 문구(`위험도 낮음`·`위험도 보통`·`위험도 높음`)로 가른다. 그런 기록이 없으면 "알 수 없음"이다.
- **PR 크기**: 추가 + 삭제 줄 수의 중앙값과 400줄을 넘는 PR의 수(Q9의 경고 기준). 계획 파일과 문서의 줄도 들어 있다.
- **발산 감지 횟수**: runner 로그에서 기간 안의 `review-diverged`·`review-reverted` 이벤트 수.
- **3회 방법 전환 횟수**: id의 날짜가 기간 안인 계획의 "의사결정 로그"에서 `- 방법 전환(`으로 시작하는 줄의 수(절차서 6절의 형식). 계획 id별 수를 함께 적는다.
  - 계획은 명령을 실행한 체크아웃의 `docs/exec-plans/active/`와 `completed/`에서 찾는다(단일 파일 계획과 폴더 계획의 `plan.md`). id의 날짜(`YYYYMMDD`)는 시간대 보정 없이 기간의 날짜와 그대로 견준다.
  - 실패 키별 3회·5회 횟수는 잴 수 없다: 실패 기록(`attempts.jsonl`)이 worktree와 함께 지워진다(TD-57). 횟수는 이 방법 전환 줄과 위 중단 보고 댓글로 센다.
- **PR당 검증 사용량**: 파일럿 판정 지표의 "PR당 사용량"(판정 워크플로 시간, 판정 수)으로 본다. 따로 세지 않는다.
- **"검토 필요" 문서 수**: `doc-lint`의 `R8 검토 필요` 경고 수(`review_cycle: on-change`인 문서의 `related_code`가 문서보다 나중에 커밋됐다). 기간과 무관한, 명령을 실행한 체크아웃의 현재 값이다.
- **하네스 자체 테스트 통과율**: `self-test --out <파일>`이 쓴 보고서에서 `pass`인 시나리오 수 ÷ 전체. 보고서를 주지 않으면 값 대신 "보고서 없음"이다. `self-test --live`의 보고서는 형식이 달라 받지 않는다.
- **runner 연속 실행 시간과 멈춘 이유**: runner 로그(`<공유 git-dir>/harness/runner.jsonl`)에서 작업자별로 `start` 이벤트와 그 뒤 첫 `exit` 이벤트를 한 번의 실행으로 묶는다. `start`의 시각이 기간 안인 실행의 수, 실행 시간의 중앙값·최댓값(분), `exit`의 이유별 수.
  - `exit` 없이 다음 `start`가 오거나 로그가 끝난 실행은 "종료 기록 없음"으로 세고 시간에서 뺀다. 이유는 runner가 정한 값일 때만 그 이름으로 세고 아니면 "그 밖"이다.
  - 명령을 실행한 머신의 로그만 본다. JSON이 아니거나 시각·이벤트 이름이 없는 줄은 건너뛰고 그 수를 "읽지 못한 로그 줄"로 적는다.
- **step당 세션 수·재시도 수**: 기간 안의 `session-start` 이벤트를 계획과 step으로 묶은 묶음마다의 세션 수의 중앙값·최댓값, `attempt`가 2 이상인 세션의 수. 계획 수립 세션처럼 step이 없는 세션은 계획마다 한 묶음이다.
- **"세션은 완료라 했지만 AC 실패" 횟수**: 범위로 낸다. runner는 AC가 모두 통과해도 뒤따르는 `check`가 실패하면 같은 `judge-fail` 이벤트를 쓰고 AC 결과를 따로 남기지 않는다(TD-58).
  - "AC 실패 확인": `check`는 통과했다고 적힌 `judge-fail`. 표준 검사가 통과했으니 AC가 실패한 것이다.
  - "AC 결과 미확인": `check`가 실패했다고 적힌 `judge-fail`. AC가 함께 실패했는지는 이 로그로 가를 수 없다.
  - 지표 값은 "확인" 수 이상, "확인 + 미확인" 수 이하다. 적힌 꼴이 다른 것은 "그 밖"으로 따로 센다.
- **발견 사항의 처리 분포**: id의 날짜가 기간 안인 계획의 "발견 사항" 섹션에서 최상위 목록 항목마다 `→ 처리:` 뒤를 본다. 마크다운 링크가 있으면 "문서 반영", `#숫자`나 `TD-숫자`가 있으면 "Issue·TD", `해당 없음`이면 "해당 없음"이다. 한 항목에 여럿이면 이 순서로 먼저 맞는 것 하나로 센다.
  - `→ 처리:`가 없거나 뒤가 이 셋에 맞지 않으면 "처리 표기 없음"이다. `- 없음` 한 줄은 발견 사항이 아니라 세지 않는다.
- **잴 수 없는 지표**: 값 대신 이유와 기술 부채 번호를 적는다.
  - PR 크기 경고·범위 이탈 경고 수(R15, R18): 게이트가 없다(TD-6). PR 크기는 "400줄을 넘는 PR 수"로 대신 본다.
  - 위험 작업·제작자 권한 명령 차단 횟수(R13, R14, R20): L1 훅이 차단을 기록하지 않는다(TD-55).
  - 구독 한도 때문에 검증이 보류된 횟수(Q12): 한도와 그 밖의 검증자 장애를 가르는 기록이 없다(TD-56). "실패로 끝난 판정 워크플로 실행" 수로 대신 본다.
  - 실패 키별 3회·5회 횟수(TD-57), "세션은 완료라 했지만 AC 실패"의 정확한 수(TD-58)는 위에 적었다.
