# 핵심 원칙

모든 규칙은 아래 원칙 중 하나 이상을 근거로 한다. B는 Beliefs이며 리뷰 지적 등급 P0~P3과 다르다.

| #   | 원칙                                   | 의미                                                                                         |
| --- | -------------------------------------- | -------------------------------------------------------------------------------------------- |
| B1  | 리포에 없는 지식은 존재하지 않는다     | 메신저·회의·머릿속의 결정은 리포 문서로 옮겨야 에이전트가 쓸 수 있다                         |
| B2  | 백과사전이 아니라 지도를 준다          | 진입 문서는 짧게, 깊은 정보는 링크로 점진적으로                                              |
| B3  | 문서로 부족하면 코드로 승격한다        | 반복해서 어겨지는 규칙은 린트·구조 테스트·체크로 바꾼다                                      |
| B4  | 실패는 신호다                          | 막히면 "더 열심히"가 아니라 빠진 도구·가드레일·문서를 찾아 리포에 반영한다                   |
| B5  | 에이전트가 직접 검증할 수 있어야 한다  | 앱 실행, UI, 로그를 에이전트가 읽고 조작할 수 있게 만든다                                    |
| B6  | 엔트로피는 매일 조금씩 수거한다        | 드리프트는 정기 작업으로 작게 정리한다                                                       |
| B7  | 경계는 엄격하게, 경계 안은 자유롭게    | 불변 조건은 강제하고 구현 방식은 맡긴다                                                      |
| B8  | 지루한 기술을 우선한다                 | 안정적이고 리포 안에서 이해 가능한 의존성을 고른다                                           |
| B9  | 되돌릴 수 없는 작업은 권한으로 막는다  | 명령 차단은 우회될 수 있다. 자격증명이 없으면 실행 자체가 불가능하다                         |
| B10 | 루프는 작고, 수렴해야 한다             | PR은 작게, 리뷰는 라운드마다 범위가 줄어야 한다                                              |
| B11 | LLM은 차단을 더할 수만 있고 풀 수 없다 | 위험도를 내리거나 P0을 닫으려면 다른 근거(두 검증자 동의, 기계 검사, 제작자 승인)가 필요하다 |

## 황금 원칙 (초기안)

1. 직접 만든 헬퍼보다 공유 유틸리티를 쓴다. 불변 조건을 한곳에서 관리하기 위해서다.
2. 데이터는 경계에서 파싱·검증한다. 추측한 형태로 다루지 않는다.
3. 로그는 구조화 로깅만 쓴다(`timestamp`, `level`, `event`, `context`, `plan_id`).
4. 파일 크기 상한을 지킨다(수치는 프로파일이 정한다).
5. 이름 규칙을 따른다(규칙은 프로파일이 정한다).
6. 불투명한 의존성보다 지루하고 안정적인 기술, 또는 작은 자체 구현을 고른다(B8).

## 피드백 승격 경로

리뷰 지적·반복 실수는 처음에는 문서에 규칙으로 적고, 반복되면 린트·구조 테스트로 승격한다. 에러 메시지에는 수정 지침을 넣는다.
