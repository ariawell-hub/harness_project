# Actions 비용: 보존 기록과 문서 검사

비공개 리포에서 하네스를 돌릴 때의 Actions 비용을 잰 입력과, 그 값을 적은 문서([docs/harness/actions-cost.md](../../docs/harness/actions-cost.md))를 입력과 견주는 검사를 둔다(계획 `20261121-actions-cost-design`).

| 경로                          | 내용                                                                                                        |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `<날짜>_<날짜>.jsonl`         | 보존 기록. `actions-cost --save`가 남긴 그 기간의 입력이다. 첫 줄은 머리(기간, 줄 수), 이어서 job마다 한 줄 |
| `2026-11-17_2026-11-20.jsonl` | 기준선의 보존 기록(2026-11-22에 쟀다)                                                                       |
| `check-doc.ts`                | 문서의 구조와 값을 보존 기록과 견준다(어긋나면 종료 코드 1). GitHub을 읽지 않는다                           |
| `test/`                       | `check-doc.ts` 테스트                                                                                       |

보존 기록에는 계산에 드는 값만 있다: 실행 id, 시도, 허용 목록에 있는 워크플로·job 이름, 날짜, 돈 초, 러너 라벨, PR 번호, head 순번. 커밋 SHA, 브랜치 이름, PR 제목은 없다.

하네스 리포의 `tsconfig.json`·`check`는 `lab/`을 검사하지 않는다. 테스트는 아래 명령으로 따로 돌린다.

## 보존 기록을 손으로 고치지 않고 덮어쓰지 않는다

보존 기록이 기준이다. 잰 뒤에 누가 그 기간의 실행을 다시 실행하거나 실행 기록이 지워지면 GitHub을 다시 읽은 값은 달라진다. 그래도 보존 기록을 바꾸지 않는다. `--save`는 이미 있는 파일을 덮어쓰지 않고 실패한다. 포매터(`fmt`)는 `.jsonl`을 건드리지 않는다.

## 절차

리포의 루트에서 돌린다.

다시 잴 때(절감 수단을 넣기 전과 뒤):

```bash
node scripts/harness.ts actions-cost --since <날짜> --until <날짜> --save lab/actions-cost/<날짜>_<날짜>.jsonl
node scripts/harness.ts actions-cost --from lab/actions-cost/<날짜>_<날짜>.jsonl
```

1. 첫 명령이 GitHub을 읽어 보존 기록을 남긴다(실행 수만큼 조회해 몇 분에서 십몇 분 걸린다).
2. 둘째 명령의 출력에서 "기록 칸" 행을 문서의 "기록" 표에 옮긴다. `수단`, `보존 기록`(파일 이름), `판단`을 채운다.
3. 검사와 테스트를 돌린다.

```bash
node lab/actions-cost/check-doc.ts
node --test lab/actions-cost/test/check-doc.test.ts
```

워크플로·job 이름이 바뀌면 같은 보존 기록의 `--from` 출력이 달라진다(이름은 체크아웃의 워크플로 파일에 있는 것만 낸다). 그때는 기준선의 보존 기록으로 다시 계산한 출력을 문서의 표식 구간에 붙인다.

## 검사가 보는 것

`node lab/actions-cost/check-doc.ts [--doc <파일>] [--dir <보존 기록 폴더>]`. 기본값은 `docs/harness/actions-cost.md`와 이 폴더다.

- 여섯 절(왜 재는가, 재는 방법, 예산, 기준선, 판단 절차, 기록)이 한 번씩, 정한 순서로 있다.
- "왜 재는가"와 "재는 방법"에 본문과 정한 낱말이 있다.
- "예산"의 네 줄이 제작자가 정한 값과 같다(`check-doc.ts`의 `BUDGET`).
- "기준선"의 표식 구간이 기준선 보존 기록으로 계산한 출력과 같다. 잰 날짜, 잰 명령, 다시 계산하는 명령이 표식 구간 밖에 있다.
- "판단 절차"의 여덟 항목마다 내용이 있다.
- "기록" 표의 행마다 여섯 칸이 그 행의 보존 기록으로 계산한 값과 같고, 판단이 계산한 값과 맞다.

코드 블록 안의 줄은 절·예산 줄·판단 절차의 항목·표·표식으로 치지 않는다(글로는 친다). 판단 절차의 내용은 그 항목에 속한 줄(머리 뒤의 글과 두세 칸 들여 쓴 이어지는 줄)만 센다. 잰 명령과 다시 계산하는 명령은 코드(백틱이나 코드 블록)로 적은 글 전체가 같아야 한다. 링크의 주소는 글로 세지 않는다. 기록 표의 앞뒤에는 빈 줄을 두고, 기록 절에서 `|`는 표의 줄(`|`로 시작한다)에만 쓴다. 예산의 네 줄과 판단 절차의 여덟 항목은 한 곳에만 적는다(그 이름이 든 줄이 더 있으면 실패한다).

## 문서의 형식

검사는 Markdown을 해석하지 않는다. 아래 형식으로 쓴 문서만 읽고, 벗어난 줄은 화면에 바르게 보이더라도 `형식(<N>째 줄): …`으로 거부한다. 해석을 흉내 내면 화면과 어긋나는 자리마다 가려진 글이 통과하거나 바른 문서의 뒤쪽이 가려진다(코드 판정에서 세 번 나왔다). 형식을 벗어난 줄은 그 줄만 오류로 내고 뒤의 줄은 그대로 읽는다.

- 머리말(frontmatter)은 첫 줄의 `---`부터 다음 `---`까지다. 본문에는 가로줄(`---`)과 밑줄 제목(`===`, `---`)을 쓰지 않는다. 제목은 `## `로 쓴다.
- 코드 블록은 줄 머리의 백틱 세 개(뒤에 공백 없이 언어 이름만)로 열고 줄 머리의 백틱 세 개로 닫는다. 들여 쓴 코드 블록, `~~~`, 백틱 네 개 이상은 쓰지 않는다. 블록 안에는 백틱 세 개로 시작하는 줄을 쓰지 않는다.
- 줄 머리는 세 칸까지만 들여 쓴다. 공백은 보통 공백만 쓴다(탭, 줄바꿈 없는 공백, 전각 공백을 쓰지 않는다). 빈 줄은 공백과 탭만 있는 줄이다.
- HTML 태그와 주석을 쓰지 않는다. `<`는 코드(백틱, 코드 블록) 안에만 쓴다. `|`가 있는 줄(표)에서는 백틱 안에도 쓰지 않는다. 표식은 줄 전체가 표식인 두 줄뿐이다.
- 역슬래시를 쓰지 않는다(코드 블록 안은 된다).
- 백틱의 짝은 한 줄 안에서 맞춘다.
- 참조 정의와 각주(`[이름]: 주소`), 그림을 쓰지 않는다. 링크는 `[글](주소)` 꼴로, 주소에 공백·괄호·따옴표·`|` 없이 쓴다(제목을 달지 않는다).

표식 구간 안의 줄은 계산한 출력과 글자 그대로 견줄 뿐이라 형식을 보지 않는다.

## 검사가 보지 않는 것

글의 옳고 그름은 보지 않는다. 설명이 사실과 맞는지, 판단 절차가 쓸 만한지는 PR 검증이 본다. 보존 기록이 잰 때의 GitHub 기록과 같았는지도 보지 않는다(다시 읽으면 달라질 수 있어 볼 수 없다).

화면에 어떻게 보이는지도 다 보지 않는다. 형식은 검사가 줄을 잘못 읽는 길(주석, HTML, 이스케이프, 들여 쓴 코드, 참조 정의, 링크의 제목)을 막을 뿐이다. 수식(`$…$`) 안의 글, 취소선, 글자 모양으로 뜻을 바꾼 글, 보이지 않는 글자는 가리지 못한다. 인용문(`>`) 안이나 목록 아래에 들여 쓴 절·예산 줄·항목·표는 읽지 않아 "없다"로 실패한다. 화면에 어떻게 보이는지는 PR 검증이 본다.
